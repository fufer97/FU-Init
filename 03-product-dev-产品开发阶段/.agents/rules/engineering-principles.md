# 开发阶段通用工程行为规范（Engineering Principles）

> 这些通用工程规范适用于本开发阶段下的所有代码工程。用户的明确指示，以及具体子工程内的项目级 `AGENTS.md` 文件，具有更高优先级。

## 1. 默认工程行为

- 在满足当前请求并遵循现有架构的前提下，交付最小且完整的改动。
- 提问前先检查相关上下文（`Raw/`、`docs/`、现有源码）。只指出那些可能实质性改变行为、范围、风险、成本或不可逆影响的假设。只有在无法安全消除这类歧义时才提问；否则采用合理假设继续推进，并说明该假设。
- 优先采用简单、直接的方案。不要添加推测性的功能、仅使用一次的抽象、用户未要求的可配置能力、兼容层，或为尚未出现的未来需求提前过度设计。
- 精准控制改动范围，保持现有风格。不要重构、重新排版或清理无关代码。只删除本次改动产生的未使用代码；发现无关问题时报告即可，不顺手修复。
- 每个修改过的文件和每一行改动，都必须能追溯到当前请求、必要的一致性维护，或对所请求行为的验证。

## 2. 规格文档与单一事实源

- 产品开发规格链默认以单一的简体中文版本维护，包括 PRD（仅完整开发模式）、产品总规格（Product Spec）、功能地图（Feature Map）、功能规格（Spec）、实施计划（Plan）、任务清单（Tasks）、架构说明（Architecture）和验证记录（Verification）。
- 不为这些规格文档创建重复副本或翻译台账，除非用户明确要求。
- 在「设计 + 开发精简联动模式（`mode: linked`）」下，外层 `../Raw/` 中由 `02-产品设计阶段` 移交的业务 PRD、页面 Demo 版 PRD 与字段清单即需求的权威上游，工程内不再重复维护 `docs/PRD.md`，由 `docs/specs/product-spec.md`（`PSC-NNN`）直接承接并向下游 Feature 与 Evals 提供唯一合同锚点。

## 3. 兼容性与既有行为

- 在现有模块中适配或新增功能前，先梳理受影响的用户流程、入口与出口、状态转换和相关契约。不要仅为使新路径可用，就导致原本有效的行为消失或意外改变。
- 当改动涉及面向用户的名称、操作、状态、顺序或其他共享产品语义时，检查直接关联的用户旅程中同一概念的其他呈现方式，对齐受同一产品契约（`PSC-NNN`）约束的部分。

## 4. 范围与边界情况

- 只有在以下情况之一成立时，才将边界情况纳入当前范围：用户明确要求；上游 PRD / Spec 明确规定；已有证据能够复现；属于高频主路径；或由本次改动直接引入。
- 不要将一个范围明确的任务扩大成通用重构、架构迁移或全仓库穷尽式测试矩阵。

## 5. 验证与停止

- 对非简单任务，先定义简短、可验证的成功标准；对简单任务，直接执行。
- 使用范围最小且相关的检查，验证修改后的行为及其直接影响的路径。
- 每个检查项只采用一种合适的验证方法，不通过多种方法重复执行等价检查。
- 某项结果一旦得到验证，就应信任并复用该结果，除非其输入或相关证据发生变化。
- 验收标准通过且当前范围内没有剩余阻塞项后，立即停止。

## 6. 产物与存储管理

- 除非仓库约定或用户明确要求纳入版本管理，否则不要将临时生成结果、依赖目录（`node_modules/`）、虚拟环境、录制文件、浏览器配置目录及其他可再生临时产物放入 Git。
- 当任务产生长期保留的构建产物（如用于发布至 WorkBuddy 资料库的单文件 `dist/index.html`）时，在交付说明中清晰报告其路径、用途、大小与构建命令。

## 7. 凭证与安全红线

- 不得主动读取、解析、枚举、回显、打印、截图或提交任何本地真实密钥与凭证文件。
- 任何计费模型调用、外部系统写入或云端公开部署，必须事先获得用户的明确授权。

## 8. 浏览器自动化与 Skills 纪律

- 本地 Web 界面测试、交互验看和截图，默认使用宿主内置 Browser 子代理。
- 一个 Agent 能完成的工作，不滥用嵌套子 Agent；如调用外部子代理，严格遵守宿主委派规范。
- 项目级 `AGENTS.md` 只保留项目专属内容（目录结构、真实命令、业务契约、完成标准），不重复抄写本通用规范。
