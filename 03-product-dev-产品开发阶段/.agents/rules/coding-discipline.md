# Coding Discipline（编码纪律）

> 参考 Andrej Karpathy 行为准则，用于减少 AI 编程中的常见失误。
> **取舍原则**：以下准则偏向谨慎而非求快；极简修改可按常识灵活处理。

## 1. 先想清楚再写代码（Think Before Coding）

**不猜测、不掩盖困惑、主动暴露取舍。**

动手编码前：
- 明确列出你的假设；不确定就问，不擅自拍板。
- 存在多种理解或实现方案时，全部列出供用户选择，不静默择一。
- 如果有更简单的方案，直接提出；必要时敢于反推或提醒过度设计。
- 遇到模糊点立即停下，指明哪里不清楚并向用户确认。

## 2. 简洁优先（Simplicity First）

**用最少的代码解决当前问题，拒绝臆测。**

- 不增加需求之外的功能、配置项或扩展口。
- 不为只用一次的代码提前做抽象。
- 不为不可能发生的场景编写冗长错误处理。
- 能用 50 行写清的代码，绝不写成 200 行。

交付前自检：「资深工程师会觉得这太复杂了吗？」如果是，先做减法。

## 3. 外科手术式修改（Surgical Changes）

**只动必须动的地方，只清理自己制造的冗余。**

修改已有代码时：
- 不顺手“优化”相邻代码、注释或格式化排版。
- 不重构没有坏掉的既有代码；严格遵循现有代码风格。
- 发现无关的死代码，仅提示用户，不擅自删除。
- 只清理因**本次修改**导致的未使用 import、变量或函数。

检验标准：每一行变更都能直接追溯到用户的明确要求。

## 4. 目标驱动执行（Goal-Driven Execution）

**先定义验收标准，闭环验证后再交付。**

将编码任务转化为可验证目标：
- 「增加校验」→「先写覆盖非法输入的测试/用例，再让其通过」
- 「修复 Bug」→「先复现问题（测试或最小复现步骤），再验证修复通过」
- 「重构模块」→「确保重构前后既有测试与核心链路均通过」

多步任务先给出简短计划并逐项闭环：
```text
1. [步骤] → 验证：[检查点]
2. [步骤] → 验证：[检查点]
3. [步骤] → 验证：[检查点]
```

---

**准则生效信号**：diff 中无关变更更少、因过度设计导致的返工更少、澄清问题发生在写代码之前而非出错之后。
