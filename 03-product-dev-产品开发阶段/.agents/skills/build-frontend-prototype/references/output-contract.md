# 需求到原型的目录与产物约定

本流程用直观、可点击的展示帮助双方讨论未来的使用方式。03 记录原型的整体系统设计、代表性场景与呈现意图，04 按同一设计提供演示载体；目录完整不等于产品完整，也不要求按完整系统的实现深度填充这些目录。

## 根目录与命名

**工作区根目录**是本轮需求材料和项目级 `.agents/skills/` 所在的项目边界。**原型源码根目录**是工作区下的 `docs/04_frontend-prototype/`，默认直接放 HTML、CSS 和 JavaScript；采用框架时它也是工程根目录。两者不能混用；设计记录始终位于外层工作区的 03 目录。

新项目采用两位阶段编号、下划线和固定用途名称。以下目录名是默认规范，不再由每次执行临时翻译或改写。用户明确指定的路径和项目现有有效约定优先。

```text
工作区根目录/
├── AGENTS.md
├── .agents/skills/
├── 原始需求资料/                         # 沿用用户已有来源位置，不改原文
└── docs/
    ├── 01_normalize-project-requirements/
    │   ├── index.md
    │   ├── 客户需求/
    │   ├── 业务约定/
    │   └── 沟通记录/
    ├── 02_requirement-playground/
    │   ├── board-data.json
    │   └── index.html
    ├── 03_prototype-design/
    │   ├── design.md
    │   └── verification.md
    └── 04_frontend-prototype/
        ├── README.md
        ├── index.html
        ├── <业务页面>.html              # 按整体设计中的页面职责命名，单页原型可省略
        └── assets/
            ├── styles.css              # 共享视觉样式
            ├── app.js                  # 必要交互；复杂时按页面拆分
            └── mock-data.js            # 有模拟数据时集中维护
```

这是阶段产物清单，不是初始化时必须创建的全部目录。只在实际执行对应阶段时创建其必要文件；不建立空壳、占位文档或第二份当前版本。04 内的页面名按场景确定，上图不是固定业务模板；只有实际使用 npm、构建工具或框架时才增加 `package.json`、锁文件、`src/` 和必要配置。`04_frontend-prototype/` 直接承载原型，不在其中再放一个 `OrderFulfillmentPrototype/`，也不在工作区根目录额外创建同用途工程。业务名称用于页面标题、README 和实际存在的工程元数据，不改变阶段目录名。

## 每个阶段负责什么

| 阶段 | 负责技能 | 输入与输出 | 完成边界 |
| --- | --- | --- | --- |
| 01 需求资料 | `normalize-project-requirements` | 从用户指定来源整理三类需求资料，形成索引 | 来源与确认状态可追溯，不补造业务结论 |
| 02 需求看板 | `review-project-requirements` | 读取 01 或直接读取指定文档，生成痛点、功能、效果看板 | 功能表达清楚，不等于甲方批准或业务已实现 |
| 03 体验原型设计 | `build-frontend-prototype` | 组织需求、业务对象、功能关系和共享状态，明确页面空间、列表浏览、滚动与操作承接，再细化代表性场景 | 本轮核心需求有归属，设计能指导实际使用；不要求预先存在 UI 稿或技术架构 |
| 04 可点击体验展示 | `build-frontend-prototype` | 按 03 的设计，用一致的模拟内容和可操作的浏览、处理与返回路径呈现，在实际页面验看 | 页面组织支持本轮工作，相关功能共同表达业务结果；不追求完整业务引擎或生产功能实现 |

已有需求材料即可调用原型技能。没有 01 或 02 的标准化产物时，直接引用用户提供的文件；不要为补目录而重新调用前置技能。编号是职责顺序，不是额外审批点或安装依赖。

## 03 与 04 的文件职责

- `03_prototype-design/design.md`：在同一份记录中说明沟通目标、需求归属、业务对象、功能配合、共享状态与结果，再细化代表性场景、页面空间与交互、记录规模及浏览方式、滚动与返回上下文、模拟方式及待讨论项，并注明唯一工程路径；对应关系供设计和审阅使用，不要求把这层说明搬进业务页面；按实际甲方反馈更新。
- `03_prototype-design/verification.md`：简短记录核心需求的实际体现、功能配合与信息一致性、代表性场景的业务结果，以及适用的列表浏览、比较、返回和工作承接观察，保留必要运行检查及未验证项。不是完整系统测试报告；没有查看或运行的内容不写“通过”。
- `04_frontend-prototype/README.md`：给使用者启动命令、执行目录、演示顺序、讨论重点、模拟内容与恢复方式；相对链接到 `../03_prototype-design/design.md`。
- `04_frontend-prototype/index.html`：默认体验入口；其他 HTML 页面按整体设计中的职责组织，不为每条场景链路各建一套页面；用相对链接互通，弹窗和局部反馈不必另建页面。
- `04_frontend-prototype/assets/`：默认存放共享 CSS、必要的 JavaScript、集中模拟数据及实际用到的资源。共用视觉规则和数据，避免逐页生成互不一致的样式与内容。
- 可选工具配置：仅按实际依赖生成；采用框架时沿用其源码结构和锁文件，模拟数据放在 `src/mocks/` 或等价位置，不强制制造路由、状态库、图表或后端目录。
- `node_modules/`、`dist/`、浏览器 profile 和截图等可再生产物遵循项目忽略规则，不作为规范要求的版本化交付物。

`design.md` 使用相对路径链接 `../04_frontend-prototype/README.md`，使资料和工程双向可达。只设计时先记录计划路径，尚未生成的文件不做失效链接；实现后补链接。

## 调用与迭代

- **只整理需求**：只执行 01，不自动生成看板和代码。
- **只生成需求看板**：只执行 02，读取现有需求。
- **只做原型设计**：生成或更新 03 的 `design.md`，不创建 04 工程和验收记录。
- **生成沟通原型**：先在 03 形成整体系统设计并细化代表性场景，再在 04 做出统一的可点击展示，最后把整体体验与必要运行检查写入 03；本轮核心需求不能遗漏，暂不展开项明确记录，不扩展为完整系统开发。
- **根据反馈迭代**：更新同一份设计与同一个工程，只验证受影响路径，不再创建 `v2`、`new` 或日期命名的平行工程。

## 已有项目和旧路径

先定位已有有效的需求索引、看板、设计记录与工程。项目已明确的入口继续有效；记录其与 01—04 阶段的对应关系，不因新版默认路径再生成一份相同内容。对旧版 `docs/prototype/` 或根级业务工程，若本次只要求迭代，直接沿用并在设计记录中写明实际路径。

用户要求迁移到本规范时，先检查已有文件、入口、相对引用及运行方式，再移动原有产物，同步项目 `AGENTS.md`、README、来源路径和受影响命令。保留业务内容和用户改动，不用复制整套工程充当迁移，不移动不同用途但编号相同的资料目录。无法安全合并的实际冲突再向用户说明。
