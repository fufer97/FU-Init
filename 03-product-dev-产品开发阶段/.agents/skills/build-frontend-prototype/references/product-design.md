# 从业务需求到可操作的应用界面

在整体业务设计之后、关键页面实现之前使用，适用于体验原型和正式应用的首次构建、局部迭代。用户明确要求的讲解页、营销页或大屏按各自用途设计。这里约束产品体验，不决定技术栈、后端能力或交付范围。下文“设计记录”指项目已有的前端设计或相关 Feature Plan；原型使用 03 中的 `design.md`，正式工程不必另建原型目录。

## 1. 从日常工作确定页面职责

先结合需求判断使用者的任务、频率、共同处理的对象和通常面对的信息量。区分已知事实与设计假设：没有实际记录规模时，在设计记录中写明用于设计的假设，不把几条演示数据当成业务上限。

用“用户来到这里要完成什么工作”定义页面，再决定信息和操作。列表负责定位与筛选，详情负责理解和处理选定对象，比较负责看清差异，工作台负责持续操作与结果反馈；一页可以承担相关职责，但不能只把所有功能各放一张卡片来替代布局设计。

应用页面、讲解页面和营销页面的组织依据不同。应用页面优先呈现当前对象、状态、可用操作和结果；有讲解用途的页面可以按阅读顺序展开。HTML、单页实现或模拟数据都不意味着要把系统做成长篇说明页。

沿用整体设计中的全部核心需求和对象关系。代表性场景用于检查同一个系统的使用方式，不能为做透一个案例而自行删去其余已纳入范围的主要功能。

### 先确定用户看见的业务名称

实现菜单、标题、按钮和详情之前，从本轮资料中核对主要对象的称呼、编号及状态含义，在设计记录中简记“来源字段或约定 → 显示名称 → 编号用途”。复用已有业务词汇，不另建全量术语库，也不逐个询问已有明确依据的名称。

- **名称有依据**：从客户用语、主数据或已确认业务定义取得名称。例如台账记录 `EQ-17` 的名称为“二号包装线”，设备列表和问题标题应先让人看到“二号包装线”，编号用于区分与追溯。不能根据代号自行猜一个业务名称；缺少名称时显示“设备名称待核实”及原编号。原型自拟名称属于模拟内容，记录其性质，不冒充来源事实。
- **区分标识用途**：用户日常确实用来定位的订单号、工单号、批次号可以保留为主要标识；内部数据库 ID、运行 ID、字段键和工程代号不充当业务名称。版本、提取方式等低频技术信息按需展开；面向技术人员的页面按其实际任务保留必要术语，不机械禁止所有编号或英文。
- **按任务命名**：导航、页签和主操作说明用户查看或处理什么；不要直接复制 API、Feature、数据表或助手推理阶段的名称。“事实与条件”“结果回流”不能仅因内部这样分层就成为菜单，应按场景表达为“交付准备”“更新订单进展”等；这些是示例，不是固定替换词。
- **状态不能只翻译字面**：结合对象解释 `pending` 是待检验、待审批还是待回复。待批准、已批准、已执行分别表达；把“生成建议”命名为“安排发货”会制造错误承诺。名称、按钮作用和可观察结果必须相符。
- **同一概念沿旅程一致**：核对列表、详情、关联选择器、图节点、方案和处理记录中直接相关的称呼。显示名称和稳定业务身份分开；历史内容按对应版本解释，原始证据和来源字段保留原文，不用全局字符串替换改写事实。

## 2. 先定空间与交互，再选组件和视觉

为关键页面在已有设计记录中用简短草图、表或文字说明：

- **主工作区**：主要任务、需要同时看到的信息和结果，占据什么位置与空间。让判断和操作所需的内容靠近，避免重要结论挤在窄侧栏，主体却只展示说明。
- **导航与上下文**：如何知道所在位置、当前业务对象，怎样前往关联工作并返回。按实际需要保留全局导航、页内切换或对象摘要，不固定套用侧栏或工作台。
- **辅助信息**：证据、历史和补充细节何时需要，适合并列、展开、抽屉还是独立页面。需要频繁对照的内容不要反复藏进弹窗，偶尔查阅的长资料不必全部铺在主工作区。
- **交互模型**：哪些动作改变选定对象、筛选范围或业务结果；切换后什么保持不变，什么必须更新。按钮名称、附近说明和实际结果要表达同一件事。

结构选择要能说明如何帮助完成任务。表格适合按共同维度扫描记录或比较差异；卡片适合有独立内容结构或可直接操作的对象；分栏适合需要同时保留上下文的处理；独立详情适合展开一个对象。按当前任务取舍，不把这些形态规定为所有页面的必选项。

### 详情页签和入口落点一起设计

同一对象有多组相对独立的阅读或处理任务时，考虑页签；需要同时比较的信息放在同一视野，简单表单或短详情不必拆签。不能把所有内容堆成长页，也不能为了形式完整给每个链接都加一组页签。

- 按用户任务划分，例如资产详情可分“使用安排 / 维护记录 / 相关资料”，而不是照搬后端模块。数量、名称和分组来自当前业务，不统一套用某个案例的五个页签。
- 名称、关键状态和必要主操作作为对象上下文保留。默认签承接最常见任务；“查看检验记录”应直接落到对应记录或页签，“补充记录”保存后应能看见新记录，不能一律跳回概况或让用户重新查找。
- 在设计记录中对主要入口简记：**从哪里点击 → 哪个对象/页面/页签 → 能看到或完成什么 → 关闭/返回去哪里**。结合任务决定刷新、前进后退和返回列表时需要恢复的对象、页签及筛选，不规定必须使用某种状态存储。
- 迭代时核对原链接和直接调用方；有实际旧链接或书签时提供对应落点或说明替代路径。页签重命名不应意外改变对象身份、业务状态或保存行为。

关系图等专用视图也按用途设计：依据已有对象与关系展示，并区分语义关系、来源关联和待核实连接；选择、拖动、缩放与编辑关系是不同能力。只读图可支持查看和移动位置，不应出现让人误以为能创建业务关系的无效控件。参考项目的截图或样式不能代替本项目数据与交互的验看。

需要参考时，定向查看与当前任务相似的真实产品页面或用户给定样例，提取具体做法及其适用条件。记录实际查看的来源；未查看的不能写成已研究。参考帮助解决布局或交互上的具体不确定性，不要求固定数量的竞品、双主题或多轮视觉方案。

## 3. 列表按记录规模和定位任务设计

订单、事项、附件等记录集合会随使用增长。为本轮主要列表明确展示哪些字段、默认顺序、如何找记录，以及超出当前视口后的浏览方式；只提供与用户任务有关的筛选和操作。

| 使用情况 | 设计取舍 |
| --- | --- |
| 持续增长、需要精确定位、核对或返回的业务记录 | 通常采用分页，结合必要的搜索、筛选与排序；避免默认把全部记录铺成整页长列表 |
| 数量少且有明确上限的选项或记录 | 可以完整展示，在设计记录中说明范围；不为形式完整增加无用分页 |
| 以连续阅读为主的动态或时间记录 | 可选加载更多或连续加载，保留定位和返回方式；不能因实现省事默认用于所有业务列表 |

选择分页时，确定合理的每页数量、翻页方式及当前范围。页码、范围、总数与筛选后的实际结果一致；只知道是否还有下一页时，不伪造总数。筛选改变后回到有效页，不能留下空白的失效页码。搜索、排序、分页共同作用于同一份结果，不只改按钮或数字。

用足以体现所选浏览方式的代表性记录呈现体验。例如选择分页，就应能实际翻到另一页并打开其中的对象；不必生成大量无意义数据。原型可使用模拟记录；正式工程沿用实际数据和接口合同，不以模拟分页替代承诺的能力。

表格的行高、列宽、字段主次应支持快速扫描。优先保留识别对象和当前决策需要的字段，将长描述放到适当的详情位置；不通过无限增高行或缩成小字容纳全部内容。记录较长、表头容易离开视口时考虑固定表头，固定操作不能遮挡内容。

## 4. 明确视口与滚动的分工

按约定展示尺寸检查首屏的业务重点、主操作和上下文。应用可以滚动，但用户不应为寻找筛选、当前对象或下一步操作反复穿越大段无关内容。

在设计中说明是整页滚动，还是由主要记录区、证据区等局部滚动，以及理由。长文阅读可以整页滚动；持续处理记录时可保留必要导航、筛选或对象摘要。不要把所有页面强锁在一屏，也不要给每张卡片增加独立滚动条。

需要比较的方案，应让关键差异在同一比较视野中容易找到，详细依据再按需展开。不能仅因为每个方案都有相同字段，就认为纵向堆放几张大卡片已经支持比较。

## 5. 保持操作上下文与工作承接

- 从列表进入对象再返回时，保留任务需要的筛选、排序、页码和合理的列表位置；刷新或前进后退的恢复范围按本轮设计实现。可用 URL、少量会话状态或浏览器原有能力，不为浏览状态新增不必要的存储层。
- 同一对象在不同页面、页签和岗位入口中保持身份与业务结果一致。新事实应更新直接受影响的原因、方案条件、下一步和证据，而不只修改状态标签。
- 页面声称的“下一步”应有相符的承接：已安排的事项能找到对应岗位和工作内容；尚未安排的应明确，并提供本轮需要的发起或补充方式；依赖外部处理的说明等待谁和什么结果。不能把用户带到空列表后再让其返回原页面。
- 在同一原型体验中演示不同岗位时，让用户知道当前以什么角色看待操作及结果，不要求真实登录。选择方案、岗位确认、接受和业务结果按实际需要区分；不为每一步统一增加一次“确认并记录”弹窗。
- 交互使用未来业务中的语义。模拟机制留在 03 与 README，不把“点击后系统会呈现……”当成每个业务动作的说明；只解释会影响当前用户决定的后果和条件。

例如：用户在筛选后的第二页打开一张订单，比较办法并形成仓储事项，仓储核对结果后，订单判断与相关方案条件随之更新；返回原列表时继续原来的工作位置。这个例子说明承接和上下文，不规定所有项目必须有这些岗位或步骤。

## 6. 用操作任务检查设计，不以内容齐全代替可用

优先检查与本轮设计直接有关的情况，不展开全套状态矩阵：

| 要验证的问题 | 可观察的证据 |
| --- | --- |
| 页面是否支持当前工作 | 能识别所在页面和对象，找到主要任务与必要操作，不依赖长篇口头讲解 |
| 名称是否来自业务且足以辨认 | 对照代表性来源，名称与编号对应正确；缺失名称未被猜写，状态未被误译；同一对象在直接相关入口仍可识别 |
| 详情分组和按钮落点是否合理 | 通过主要链接进入预期对象和页签；保存后看见对应结果；共享上下文、返回及约定的刷新恢复正确 |
| 列表增长后是否仍可定位 | 用所选分页或加载方式找到记录，范围和数量正确；少量固定列表则检查其上限假设 |
| 页面结构是否支持判断 | 在目标尺寸下看清关键结论；比较差异无需在长段内容间反复翻找 |
| 返回是否能继续原工作 | 从非初始列表状态进入详情再返回，所需筛选、页码和位置保留 |
| 下一步是否有承接 | 跟随页面明确提供的下一步，能到达相符的工作或清楚的等待状态 |
| 变化是否影响相关判断 | 处理结果能在直接关联的页面、方案条件和后续事项中一致体现 |
| 专用视图是否兑现所表达的能力 | 采用关系图时能看到来源支持的节点/边，完成所提供的选择、拖动或查看操作；只读展示没有被当作业务关系编辑 |

根据实际观察修正设计与页面，仅复查受影响项。用户要求自行验看时，交付上述适用路径并标明未检查，不改成强制浏览器自动化。把真实观察与尚待用户测试的部分分别写入已有 `verification.md`。

本指引将已审阅的全局设计材料中适用的思想重新组织为原型方法，来源与取舍见 [来源说明](provenance.md)。它不依赖另外安装或执行那些 Skill。
