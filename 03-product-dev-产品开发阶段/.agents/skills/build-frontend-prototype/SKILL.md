# 用体验原型对齐未来使用流程

**原型是双方讨论未来使用方式的工具。** 它要让人直观看到：谁在什么情境下进入系统，看见什么、操作什么，系统如何回应，下一步去哪里，最终得到什么。借助 AI 加快设计与生成，完成程度由本轮沟通目标决定。

优先表达用户与甲方希望呈现的体验。先把需求组织成一套相互配合的功能与页面，再用场景检验这套设计；不把需求条目或单条链路分别做成孤立的小应用，也不扩展为全套后台模块、业务状态机或管理表单。技术实现只需支撑本轮整体体验，模拟结果可以预置。

**实现可以简化，未来使用方式仍须认真设计。** 面向日常工作的系统页面，应考虑用户怎样定位记录、比较信息、连续处理与返回工作，不能因为采用 HTML 或只有少量样例，就将页面做成功能卡片和说明文字的纵向堆叠。

## 业务表达心法

**让客户从呈现的业务处境和结果中看懂原型解决什么问题、回应什么需求。** 这是设计取舍与表达效果的要求，不是固定的界面形式。

- 按客户真实的角色、业务对象、困难和预期改善组织场景、内容与信息主次。每个主要场景都应能说明需求依据、要解决的问题，以及客户在原型中能看见的处理方式或结果；对应关系简短记在 03 设计记录中，不要求需求与页面一一对应。
- 用有代表性的业务内容、关键差异、前后变化和结果呈现体现价值。只写功能名称或“提效、赋能、闭环”等口号，不能代替这件事；缺乏依据的效果和模拟数字不能写成真实成果。
- 需求对应关系用于指导设计和审阅，不要求在页面上增加“痛点—需求—价值”说明区、需求编号、按钮或对话。静态展示、比较、工作台、列表或交互流程都可以；只有业务体验需要用户操作时才安排相应交互，保留用户指定的呈现意图。
- 页面语言使用客户熟悉的业务对象、任务、动作与状态，避免包装性黑话、空泛口号和无业务必要的模型术语。客户行业的专业词汇及确实有助于理解的技术名称可以保留，不机械套用禁词表。
- 首次生成前核对主要业务名称的来源；有名称的设备、物料等不能只显示内部代号。保留用户确实使用的业务编号及原始依据，名称缺失不猜写。具体命名与详情导航按 [应用产品设计方法](references/product-design.md) 执行。
- 助手的需求分析、推理和设计步骤留在工作过程与设计记录中，不直接充当业务界面的结构或文案。例如“先看清问题，再进入下一步”不能替代具体的业务内容；真实业务确有操作顺序时，应表达那个具体顺序。

例如，订单履约场景可以通过受影响的订单、缺料情况、交期影响及处理结果，让客户理解系统如何帮助处理交付风险；不必额外设计一个讲解“需求是什么”的按钮或聊天流程。此例只说明设计思路，不规定其他项目的页面结构。

## 输入与目录

- 输入包括已有需求文件、沟通中的决定，以及用户希望呈现的方式、参考页面或演示重点。资料格式和数量不构成门槛；呈现方式未明确时先结合上下文提出具体方向。
- 不要求先补 PRD、详细 UI 稿或后端架构。不把原型采用的组件、模拟规则或流程假设自动升级为正式系统设计。
- 先读项目指令、指定资料和直接相关的既有页面。只设计时交付设计；已授权生成原型时继续完成演示载体与必要检查。只有会实质改变沟通目标或核心体验、且上下文无法解决的问题才询问，不增加固定的逐阶段审批。
- 按 [目录与产物约定](references/output-contract.md) 使用工作区的 01—04 目录。01/02 是已有需求输入，03 保存体验设计与验看记录，04 承载可点击页面。缺少 01/02 时直接使用指定资料，不重新整理资料或补空目录。

首次准备预览环境时读 [安装说明](INSTALL.md)。需要选择实现方式或增加依赖时读 [技术栈说明](references/stack-selection.md)；第三方心法来源见 [来源说明](references/provenance.md)。

## 第一步：明确这轮要与甲方对齐什么

按任务定向读取资料，区分已表达的需求、已确认决定、我们提出的呈现方案和待讨论假设。保留真实业务边界，不补造事实或确认结论。

先用简短描述明确：

- 谁会使用系统，在什么具体情境下开始，当前哪里不便。
- 这是日常工作的应用页面、用于讲解的展示页，还是其他明确形态；系统页面还需了解主要任务频率与记录规模，未知部分作为设计假设记录。
- 我们希望用户未来如何完成这件事，系统准备替他处理什么，哪些地方需要他判断或操作。
- 本轮需要甲方看懂、比较或确认什么，例如操作顺序、信息呈现、结果形式、岗位交接或功能范围。
- 为回答这些问题，哪些场景需要演示，哪些内容暂不展开。

先汇总本轮提供的需求与功能看板，保留来源，明确核心需求、关联需求及暂不展开的内容；不能只挑一条容易演示的链路就遗漏其他核心需求。展示深度按沟通价值和用户要求选择，不以全部需求都做成完整业务模块为默认目标。

用户要求根据需求生成整体原型、且未缩小范围时，已提供的主要功能方向默认都纳入整体设计和必要展示。可以简化模拟数据与实现深度，不能自行省略核心需求或切断其关联；局部迭代仍只处理用户指定内容及直接影响。

## 第二步：形成原型的整体系统设计

使用 [体验设计记录模板](references/design-template.md)，在同一份 `docs/03_prototype-design/design.md` 中先说明：

- **需求与功能归属**：相关需求怎样组成有业务意义的功能，哪些功能共用信息、互相支持。每项本轮核心需求都有归属和可见结果；不把需求清单直接当菜单，也不强制一项需求对应一个页面。
- **业务对象与角色**：用户共同处理什么对象，这些对象有什么关系，各岗位关注、补充或决定什么。不同功能引用同一业务对象时，名称、含义和当前情况一致；只说明体验所需的业务关系，不设计数据库或后端。
- **功能之间的配合**：哪些功能独立使用，哪些并行、交叉或相互依赖，处理结果怎样影响其他工作和原来的业务判断。不能把所有工作强排成一条流水线，也不能让相关功能各自维护互不相干的结果。
- **页面与入口组织**：按用户工作安排总体入口、页面职责和关联访问方式，让相关功能在合适的业务上下文中共同出现。整体设计不等于把所有功能塞进一页，也不预定统一队列、侧栏、工作台或对话形式。
- **共享状态与结果**：明确关键变化影响哪些信息、页面或岗位，哪些状态含义必须区分，用户最后能获得什么业务结果。只展开会影响本轮理解的部分，不补全量状态机或所有异常。

用简短说明、表或关系图表达即可，不要求同时制作多套产物。进入页面实现前，应能从这份记录看清需求归属、整体结构、功能配合与关键变化的影响；说不清的部分先补设计或标明待讨论假设，不靠增加菜单掩盖缺口。

整体结构明确后，再选择代表性使用场景细化和检验，包括设计中实际存在的多入口、岗位交接或跨功能变化。场景可以并行、交叉、回到已有工作；它们是同一系统的使用方式，不是彼此独立的产品。需要说明操作经过时写简短故事板：

**触发情境 → 用户看见的信息 → 用户操作 → 系统反馈/结果 → 下一步或结束。**

每一步写清角色、所在页面、实际输入与可见结果，以及如何使用或改变整体设计中的信息。没有用户输入或动作的展示环节，记录其信息与结果即可，不为了填故事板补操作。结尾说明原业务问题得到什么结果、还剩哪些条件；一次事项完成不能自动代表整个业务目标完成。

明确区分用户动作和系统工作。需求希望系统整理、检索、分析或生成的内容，可以用预置结果呈现这种未来体验；不要为了省实现而改成让用户逐字段填完，再点击“保存”的另一种流程。反过来，需求本来需要人工判断或确认，也不能在原型里表现为系统擅自完成。

“借助 AI 构建原型”不等于产品必须是聊天界面。是否采用对话、工作台、列表、分步引导或其他形式，按需求和用户的呈现意图决定。

## 第三步：设计页面空间、交互与视觉表达

**设计系统页面前，读取并应用 [应用产品设计方法](references/product-design.md)**，把整体业务关系落实为页面职责、主工作区、辅助信息、列表浏览、滚动与操作承接。局部修改只读取与改动相关的部分，不重做无关页面。

结构与交互选择明确后，再读取并应用 [Emil 设计心法](references/emil-design-eng.md)，打磨适用的组件反馈、动效和细节；它不替代信息架构与产品交互设计，也不要求增加动效库。

在工作区的 `docs/03_prototype-design/design.md` 简短记录：

- 页面在整体系统中的职责、承接哪些需求和相关功能，首屏必须让人看懂什么，必要操作和结果放在哪里。
- 页面的空间结构与信息主次：哪些需要同时看到，哪些常驻，哪些按需展开；所选形态如何支持任务，不只列组件名称。
- 主要列表的记录规模或假设、定位方式、默认顺序及分页或其他浏览方式；页面滚动与局部滚动怎样分工。不能因样例少就省略真实使用所需的列表设计，也不机械要求所有列表分页。
- 页面之间如何前进、返回和交接；返回时保留哪些工作上下文，页面提供的下一步由什么工作或等待状态承接。
- 详情按哪些实际任务分组，是否需要页签；主要链接/按钮落到哪个对象、页面和页签，保存、关闭或返回后看到什么。简单任务不强拆页签，不能照抄后端模块或固定案例布局。
- 具体呈现方案：关键内容、示例文案、结果样式和必要的页面草图。只写“简洁、现代、遵循最佳实践”不足以指导生成。
- 用户提供的参考或品牌要求，以及统一的字号层级、对比度、密度、间距和必要反馈。设计应适合实际展示尺寸，不能靠大量小字、淡色文字或装饰留白掩盖重点。
- 影响本轮体验的状态与分支。只展开会改变用户判断的内容，不默认制作全量空、错、加载和权限状态矩阵。

业务页面使用未来用户能理解的语言。需求追踪编号、原型假设、实现限制和验看记录留在 03 文档，不默认做成主导航或常驻说明墙；用户用于定位的业务编号、原件编号与来源位置按任务保留。确实影响当前业务判断的缺失信息、证据与审批条件，应在相关位置清楚呈现。用户明确要求辅助讲解页时可以提供，并与业务操作页面区分。

保留一个克制的演示标识即可；不要把每个操作都变成对原型实现方式的解释。既有原型需要调整时，按本轮决定记录直接受影响的保留、新增、替换或移除项。

## 第四步：用最少实现支撑选定体验

页面方案明确后再选择实现方式。**新建默认使用多页面 HTML、共享 CSS 和必要的原生 JavaScript**，无需先初始化 React 或安装组件库；只需一个页面的场景也不强行拆页。页面跳转、弹窗、抽屉和局部更新按未来使用方式设计，不把每次操作都变成跳页。

沿用已有原型的技术栈和入口，不因默认值改变而自动迁移。只有选定体验涉及大量联动状态、复杂编辑或拖拽等交互，且框架能明显减少实现成本时，才考虑 React 等方案，并在设计记录中简述原因；Vite 可按需用于预览和资源构建。详细取舍见 [技术栈说明](references/stack-selection.md)。原型技术不预定正式产品的选型，组件库也不替代页面与体验设计。

按目录约定在 `docs/04_frontend-prototype/` 创建演示工程，或更新已有唯一工程：

- 使用有代表性的模拟内容、预置结果和少量前端状态。可以预设场景或采用确定性结果，无需实现真实分析、调度或审批引擎。
- 按同一份整体设计生成页面，共用业务对象、模拟数据和状态含义。关键变化在直接受影响的页面与结果中一致呈现，不能只更新一处状态或成功提示；可用预置的前后场景表达，不追求生产级数据模型、全量 CRUD、完整状态机或跨岗位管理系统。
- 表单只要求未来用户在此步骤确实需要提供的内容。不为“看起来完整”统一增加记录人、依据编号、审批、日志或多阶段确认。
- 会影响需求理解的权限或业务约束要表达清楚，但不因此搭建真实鉴权与流程引擎；可通过预置身份、场景或结果展示。原型中的拟议规则不得写成甲方已确认。
- 演示之外的功能可以不出现，或清楚标为本轮未展开；不要用无响应按钮冒充可体验功能。也不要为了让每个菜单都可用而扩展本轮范围。
- 模拟数据集中维护，相关对象保持一致。页内交互先用内存状态；跨页只传递选定场景所需的信息，可用 URL 参数或会话级存储，避免跳页后丢失前一步的选择。采用会话级状态时提供简单重置入口，不承诺刷新即恢复，也不建立持久业务数据层。
- 所选搜索、筛选、排序和分页应实际作用于模拟记录；用足以展示所选浏览方式的内容验看，并保留必要的返回上下文。不能用无效分页控件或永久只有首屏的样例冒充已设计的列表体验。
- 保留基本可访问性、清楚的反馈和必要的焦点/关闭行为，尊重减少动态效果设置。
- 不引入真实后端、业务接口、密钥、数据库或外部执行动作；不为本轮原型补整套产品规格和技术架构。

## 第五步：按沟通目标验看

先对照整体设计核对需求归属，再从未来使用者的视角体验代表性场景，检查功能组合在一起是否讲得通：

1. 本轮核心需求是否都有具体呈现，客户能否从系统中的业务内容和结果看懂解决什么问题？明确本轮未展开的内容，不用功能名称或口号代替实际体现。
2. 页面入口和职责是否清楚，相关功能能否在同一业务上下文中配合？从不同入口查看同一对象、切换岗位或返回原工作时，信息和状态是否一致？只检查设计实际包含的这些情况。
3. 关键处理或条件变化后，相关页面与判断是否反映结果？是否仍有已处理事项却完全不影响相关业务信息的断点？保留尚未满足的条件，不以事项关闭冒充业务目标完成。
4. 不依赖长篇口头解释，能否理解当前情境、系统回应、已有结果与必要操作，用户工作与系统工作是否分明？不要为满足验看而额外添加按钮或对话。
5. 按 [应用产品设计方法的验看项](references/product-design.md#6-用操作任务检查设计不以内容齐全代替可用)，检查实际涉及的列表浏览、页面滚动、比较、返回上下文和下一步承接。能否连续完成工作，而非只读完一组卡片？
6. 关键信息是否看得清，布局与文案是否支持本轮体验？是否混入包装性黑话，或把助手的工作步骤、模拟机制当成用户流程？
7. 甲方能否据此指出整体组织、功能配合、流程或呈现哪里与预期不同？拟议方案与已确认需求是否分清？

再做支撑演示的最小技术检查：通过本地预览打开页面，检查资源加载、页面链接、本轮演示路径、必要返回和恢复操作；跨页传递了状态时，确认前后选择一致。仅在实际采用构建或类型检查工具时运行相应命令，不为纯 HTML 原型补装工具链。检查约定的展示尺寸；只有本轮要讨论移动端体验时才增加移动端验看。不默认扩展为完整回归、压力测试或全量业务规则验收。

优先使用内置 Browser（`iab`）或项目允许的独立浏览器。用户明确要求自己验看或不运行浏览器自动化时，按该要求交付可访问入口和演示路径，标明未检查项；不要为了满足 Skill 再运行自动化。工具不可用时也如实说明，不虚构查看结果。

在 `docs/03_prototype-design/verification.md` 按本轮核心需求简记实际入口、观察到的业务结果与页面操作体验、必要运行检查及未验证项，不能只写“整体链路通过”。编译通过不能证明原型表达清楚，助手验看也不能代替甲方确认。修正实际观察到的问题，仅复查受影响内容。

## 第六步：依据沟通反馈迭代

收到反馈后，先判断差异发生在需求理解、整体功能组织、未来使用流程、信息呈现还是视觉表达。涉及共用对象、功能关系或状态含义时，先更新整体设计，再同步直接受影响的页面；局部反馈只改对应内容，不每次重做整个原型。不要直接把所有反馈转成新增模块或增加字段。

在同一份 `design.md` 中记录实际反馈来源、涉及体验、修订和确认状态；更新同一个演示工程。没有甲方反馈时保留待讨论项，不编造批准或等待反馈才交付已完成的本轮演示。

## 交付与停止

交付可访问的演示入口、简短的体验路径、03 的整体设计与场景记录、04 的页面源码和启动说明。README 说明运行目录、如何开始体验、模拟内容及恢复方式；设计与工程入口相互链接。

当本轮核心需求在整体原型中有归属、相关功能与结果一致、页面组织与操作能支撑代表性工作，且必要运行检查已完成或未检查项已明确，即交付等待反馈。**原型范围内的整体体验可讨论，是完成标准；完整系统实现不是本技能的目标。** 不把页面做出、技术检查通过或一次演示，写成正式功能已经交付、技术方案已经确定或甲方已经接受。

已知的核心需求遗漏、必要入口不可达或相关结果矛盾不满足完成标准，应先修复，不能仅登记为“未验证”后宣称完成。用户要求自己验看或工具确实不可用时，可以交付待验看的版本，但须区分未检查与已发现的问题。
