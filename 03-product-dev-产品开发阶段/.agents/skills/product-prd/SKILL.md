# 产品级 PRD

把已经收敛的产品决定写成可由人和 Codex 共同消费的产品合同。只依赖对话、项目证据、Markdown
模板和本 Skill 的轻量校验器，不依赖 Spec Kit、Superpowers 或其他提示词框架。

## 输入与边界

1. 锁定唯一目标项目根，读取适用的 `AGENTS.md`、现有 `docs/PRD.md` 和用户提供的材料。
2. 先复用当前对话中已经明确的产品决定。只询问会实质改变用户、范围、核心行为、质量底线或验收的缺口。
3. 没有足够事实时保留 `draft`，把未知项写入“开放问题”；不得替用户编造目标、指标或业务规则。
4. PRD 只写 Why 与 What。技术栈、框架、数据库、目录、类、协议和部署拓扑写入 Architecture/Plan。
   外部强制技术约束只有在它会改变产品或合规边界时才可写入“依赖与约束”。
5. 一个项目只维护一份产品级 `docs/PRD.md`。不要在总 Spec 或每个 Feature 目录重复创建 PRD。
6. 背景和需求引用已有材料的路径/链接与条目，或可定位的用户指令；保留原文的确认状态和适用条件。
   资料冲突时记录差异和确认依据，不把推断或较新的记录自动当成已批准决定。

## 落盘流程

### 1. 创建或合并草稿

从 `assets/PRD.template.md` 创建 `docs/PRD.md`。目标已存在时保留有效内容和稳定 ID，只补缺失合同，
不整文件覆盖。状态先写 `draft`。

保留模板的章节入口，按当前范围控制深度。不适用的业务状态、风险或其他可选内容写明原因并移除
示例行，不为填表虚构内容。已有原型/设计仅链接并标注确认状态，不要求额外制作。

PRD 至少回答：

- 为什么做、给谁用、在什么场景使用；
- 产品目标、成功信号、判断口径和反指标；需要量化时写基线、目标、数据来源和观察周期；
- P0/P1 核心旅程及可观察完成结果；
- In-Scope、Out-of-Scope 和优先级；
- 每项需求的触发、输入、业务行为、输出、边界和恢复；
- 与产品相关、可验证的性能、安全、隐私、合规及可用性底线；
- 风险、依赖、开放问题和已确认决策。

基线未知时写明补测方式和时机；简单工具可用具体的定性判定。功能验收通过不代表业务目标已经
达成：AC 描述产品行为，业务成效按目标约定的观察方式在实际使用后判断。

PRD 只保留影响业务决定的关键规则和状态约束；统一对象、完整跨 Feature 状态机由 Product Spec
展开，局部流程由 Feature Spec 展开。后续规格引用原有需求，不复制多份可独立修改的合同。

### 2. 建立稳定追踪

- 功能需求使用 `REQ-001` 起的三位稳定编号。
- 非功能要求使用 `NFR-001` 起的三位稳定编号。
- 验收使用 `AC-001` 起的三位稳定编号。
- 每条 AC 写明来源 REQ/NFR，并包含独立的 Given、When、Then。
- 每项需求说明来源与确认依据，关联已有 GOAL/Journey，并说明优先级理由；全局 NFR 可关联目标
  或明确的外部约束，无须虚构旅程。来源链接直接复用，需求到目标的关联必须解释实际贡献。
- GOAL/Journey 编号保持稳定。更新旧 PRD 时在现有表格或邻近说明中补关联，不为了套新模板重编 ID。
- 删除或替换需求时保留变更记录；不要回收旧编号给另一个语义。

### 3. 审阅并确认产品合同

确认前读取 [内容质量审阅](references/quality-review.md)，核对依据、目标关联、取舍、可验证性与
文档深度。只报告有位置、有证据的实质缺口；已有审阅仅复查本轮变更及直接影响的部分。

向用户集中呈报会改变产品结果的决定：目标用户、核心旅程、范围、优先级、质量底线、替代路径和
仍会阻塞实施的问题。用户当前指令已经明确覆盖这些决定时，可把该指令作为确认依据；不要要求特定口令。

只有产品合同已获确认、没有阻塞型开放问题且文档不含模板槽位时，才把 frontmatter 改为：

```yaml
status: confirmed
```

普通待验证假设可以保留：正文标为假设并引用开放问题，记录影响、是否阻塞、验证方式与时机。
开放问题使用“待确认/处理中/已解决/已关闭”（亦识别 open/closed）；已关闭项写处理结论及依据。
不得仅改状态绕过阻塞问题，也不把内容审阅意见当成用户确认。

### 4. 校验

从实际加载的 `SKILL.md` 定位 `<SKILL_DIR>`，运行：

```bash
python3 "<SKILL_DIR>/scripts/validate_prd.py" "<项目根>" --require-confirmed
```

校验器检查状态、章节、REQ/NFR/AC 唯一性、AC 来源、非空 Given/When/Then 和需求覆盖；对 confirmed
文档再检查需求表必填内容、开放问题状态与关闭依据、阻塞项和模板残留。draft 允许保留待填写的表格。
来源是否充分、目标关联是否合理、规则有无矛盾由内容审阅判断；脚本通过不能代替审阅或用户确认。

## 变更规则

- 下游 Product/Feature Spec 发现新产品行为、范围或验收时，先更新 PRD 并重新确认，再调整总 Spec 与 Feature Map。
- 实现细节变化但产品行为不变时，不改 PRD。
- 已有项目只需要按代码事实补文档时，不使用本 Skill；按项目已有的文档维护约定处理。
- PRD 确认后先使用 `$product-spec` 冻结跨 Feature 总合同；总 Spec confirmed 后再使用 `$feature-spec-planning`。

## 完成标准

- `docs/PRD.md` 是唯一产品级需求事实源；
- Why、用户、旅程、范围、需求、NFR、验收、风险与开放问题完整；
- 每个 REQ/NFR 至少被一条 AC 验收；
- 重要需求的依据、目标关联和优先级理由可追溯；成功信号有可执行的判断方式；
- 文档没有实现方案污染、模板槽位或伪造事实；
- 内容审阅发现的实施阻塞已解决，其他假设保留明确的验证安排；
- 需要进入 Product Spec 与 Feature 拆分时，状态为 `confirmed` 且校验通过。
