# PRD 内容质量审阅

在草稿准备确认时使用；更新已有 PRD 时，只审阅变更与直接受影响的依据、目标、旅程和验收。
依据当前对话与已提供材料判断，只有影响结论的来源缺失或冲突才回查原文。

## 审阅重点

| 维度 | 判断内容 | 值得报告的缺口 |
|---|---|---|
| 需求依据 | 关键问题、需求与规则能定位到材料条目或用户指令；来源的确认状态和适用条件保留 | 把假设写成事实、冲突未说明、依据超出适用范围 |
| 目标与取舍 | 重要需求能说明对 GOAL/Journey 的贡献；全局约束可单独追溯；优先级反映本轮取舍 | 孤立功能、所有项都标最高优先级却没有理由、删减范围没有说明 |
| 成功判定 | 指标有可执行的判定方法；量化目标有基线或补测安排、口径、数据来源与周期 | “提升效率”没有判定方式、虚构基线、用功能验收通过代替业务收益达成 |
| 行为与验收 | 一项需求表达一个可辨识的业务能力；AC 有真实前置条件、动作和可观察结果 | “友好/快速/合理”没有边界，验收只复述功能名，规则或旅程相互矛盾 |
| 假设与风险 | 假设显式标记并关联 OQ；影响、验证方法与时机明确；重要未决项未被隐藏 | 待确认规则直接进入已确认范围、关闭问题没有结论依据、非阻塞假设没有验证安排 |
| 深度与衔接 | 细节足够支持产品决定；全局与局部规格各有职责；已有设计链接标注状态 | PRD 重复完整状态机、设计稿被默认视为批准、无关章节为填表而编造内容 |

检查 GOAL/Journey 引用能否定位到实际条目，REQ/NFR 与 AC 是否表达同一业务含义。脚本只能检查
结构与非空内容，不能证明来源真实、关联合理或用户已经批准。

业务收益例：只有“缩短处理时间”仍不足以判断成功；应说明计时起止、统计对象、数据来源、观察
周期和目标。没有基线则写补测安排，而不是自行给出一个提升百分比。定性目标也可以充分，例如在
约定试用周期内，由目标角色独立完成指定任务并记录是否需要人工协助；任务和周期仍须有用户依据。

## 如何处理发现

- 仅报告有具体位置和依据的实质缺口，按“位置 → 问题及影响 → 建议修订/待确认事项”表达。
- 阻塞核心范围、业务规则或验收的问题解决前保留 draft；不以所有未知项都清零作为确认条件。
- 非阻塞假设保留 OQ 与验证安排。来源、目标或条目是否有关联需要语义判断，不能只检查出现了 ID。
- 复用 PRD 的开放问题、决策记录和当前回复，不额外生成评分表或审阅报告；用户要求时再单独交付。
- 审阅意见是判断依据，产品决定沿用用户已有授权；没有新增决定时不重复请求确认。

## 设计参考

以下资料用于维护本审阅方法，执行 PRD 任务时无需默认联网或采用其完整流程：

- [Atlassian PRD 实践](https://www.atlassian.com/agile/product-management/requirements/)：来源、假设和设计链接。
- [Aha! PRD 指南](https://www.aha.io/roadmapping/guide/requirements-management/what-is-a-good-product-requirements-document-template)：目标、测量与按项目调整深度。
- [GitHub Spec Kit 模板](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)：优先级理由和可观察验收，仅借鉴其 Feature Spec 层面的做法。
- [BMAD PRD 质量审阅](https://github.com/bmad-code-org/BMAD-METHOD/blob/bda3c5929f672019b90f39a3ea27259d35d00974/skills/bmad-prd/assets/prd-validation-checklist.md)：决策充分性、内容实质、范围和文档适配。
