# 准备已确认需求资料

为后续 MVP 和技术架构讨论准备原始需求资料入口。默认只创建缺失目录，并告诉 FDE 对应文件应放在哪里；不生成需求正文或示例业务材料。

## 目录结构

先读取适用的项目指令，确定外层工作目录：复用用户指定路径或当前对话已确定的位置，信息不足时再询问。`Raw/` 与独立开发项目同级，不在开发项目内另建第二个原始资料区。用户已经明确原始资料目录时使用该位置。

```text
<工作目录>/
├── Raw/
│   └── confirmed-requirements/
│       ├── customer-requirements/
│       ├── communication-records/
│       └── business-agreements/
└── <开发项目>/
```

目录统一使用上述英文名；客户原文件名保持原样。只补齐三个资料目录及必要父目录，已有目录和文件保持原样；遇到同用途的既有中文目录，先说明与新结构的对应关系，不自动改名、迁移或创建重复资料副本。不要求改造 Raw 中其他业务数据的目录结构。

## 引导 FDE 放入资料

创建后展示实际路径与目录树，并说明三类资料的用途：

| 目录 | 应放入的文件 |
| --- | --- |
| `customer-requirements/` | 客户提供或双方确认的需求说明、业务目标、范围和验收约定 |
| `communication-records/` | 与需求相关、已核对的会议纪要、岗位访谈及补充沟通记录 |
| `business-agreements/` | 双方确认的业务口径、处理规则、责任边界及限制条件 |

提醒 FDE 保留原文件名、内容、日期和已有确认说明。目录名称不改变文件中的确认状态；局部待确认、尚未批准或个人判断仍保留原样。不要将未核对的材料自动认定为已确认。

FDE 可以自行放入文件。只有用户提供来源并要求复制时才执行复制：沿用已明确的类别，保留原件；同名冲突或归属不明的文件先列出，不覆盖、不猜测、不自动拆分正文。同一文件涉及多个方面时保留一个原件位置，不制造三份副本。

## 完成边界

- 核对三个目录存在且没有覆盖已有文件；列出已创建或复用的路径。
- 执行过复制时，报告已复制文件及未处理原因；尚未放入文件时如实说明，不宣称需求已经整理完成。
- 不在本步骤生成规范化文档、修改 AGENTS.md、确定 MVP 范围或设计技术架构；后续任务按用户要求使用这些资料。

## 自然语言提示词

```text
使用 $prepare-requirement-materials，在当前工作目录的 Raw/ 下准备
confirmed-requirements/，包含 customer-requirements/、
communication-records/、business-agreements/ 三个子目录。
告诉我每类应放哪些文件。先只准备目录，保留已有内容。
```
