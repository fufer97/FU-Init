# Feature 通用拆分规则

在新增或调整 Feature Map 时使用。通用化的是判断方法与检查标准；具体边界由项目的需求、共享行为合同、
现有能力与交付目标决定。不要预设功能清单、Feature 数量、行业模板或固定的拆分维度。

## 先选择拆分主线

以用户当前希望交付、验证和迭代什么为起点，结合实际职责与依赖选择主线。用户已明确希望按阶段或模块
逐步验证时，优先据此提出方案；不因为结果主要供内部消费就改回终端业务功能拆分。

| 主线 | 适用情况 | 边界依据 |
|---|---|---|
| 业务任务或用户旅程 | 重点是分批交付使用者能够完成的工作 | 一项可识别的业务结果及其完整必要流程 |
| 处理阶段 | 输入经过连续加工，每步都有可检查、可复用的中间产物 | 本阶段接收什么、完成什么转换、向下一阶段交付什么 |
| 能力模块 | 职责稳定，需要分别定位问题、优化或替换内部实现 | 明确的职责、输入输出约定、消费方和局部验收边界 |

三种主线都可成立。一个 Map 可以组合阶段、模块与业务功能，但同一结果只能有一个主责 Feature，避免
对同一工作重复计入。Feature 是规划与验收单元，不强制对应代码目录、独立服务或部署单元。

## 从材料识别交付结果

从 PRD 的用户旅程与验收条件中识别：谁在什么条件下发起、使用哪些输入、完成什么结果，以及对象或状态
如何变化；用 Product Spec 核对共享对象、状态、不变量和恢复规则。优先复用已有描述，不另建一套需求台账。

- 用一句话表达候选结果，例如“使用者完成某项操作，得到某个结果”，或“本模块接收某类输入，输出供某消费方
  使用的产物”。数据、模型、索引、转换产物等均可成为结果，前提是有真实用途与可判定的完成条件。
- 引用实际存在的 REQ/NFR、AC 与 PSC，区分来源事实、Agent 的拆分建议和影响边界的待定取舍。
- 一个需求可以跨多个 Feature，一个 Feature 也可以承接多个需求；不把每条需求、每个业务对象机械变成 Feature。
- 架构用于识别职责、输入输出和真实依赖。模块边界可以成为 Feature 边界，但不能仅按框架、服务、数据库或
  模型的数量机械分配。Map 可以先于完整架构细节形成；影响边界的未定决策要说明，实现选择留给 Architecture 与 Plan。
- 缺少范围或全局行为依据时，指出需由 PRD 或 Product Spec 补充的内容，不在拆分中添加新的产品规则。

## 明确独立验证与迭代边界

阶段或模块型候选至少说明以下内容，简短写入方案和 Map 正文即可，不另建一套报告或规格体系。

| 内容 | 必须说清的问题 |
|---|---|
| 职责与输入 | 本阶段负责什么，接收哪些输入，要求哪些已知条件；哪些工作仍由上下游负责 |
| 输出与消费方 | 交付什么产物或能力，哪些信息和状态必须保留，交给谁使用 |
| 独立验收 | 使用什么代表性输入检查输出，怎样判断正确、缺失、失败或部分完成；不只验证组件能启动 |
| 迭代边界 | 输入输出约定不变时，哪些内部处理可单独优化；什么变化会影响直接消费方 |
| 依赖与交接 | 依赖的具体产物或能力，以及对接时必须满足的业务语义和失败反馈 |

解耦允许有依赖。独立验证可以使用固定的代表性样本，不必等完整应用完成；集成时仍须验证上下游实际
交接和最终业务结果。若使用依赖替身，说明其边界，不能把局部通过当成真实链路已通过。
只有拆开名称或目录、内部仍互读未约定状态时，不能宣称已解耦。

## 形成候选并判断拆分或合并

围绕选定主线归并同一职责所需的步骤，再对边界有疑问的候选应用下列判断。无需逐对比较所有候选或计算评分。

| 判断 | 适用依据与处理方式 |
|---|---|
| 保持为一个 Feature | 相关步骤共同交付一个业务结果，或完成一项有明确消费方的阶段/模块职责；可以涉及一个或多个技术层。 |
| 考虑拆开 | 具有不同职责、可单独验证的产物和相对稳定的交接约定，并能分别定位问题或迭代；说明分开的收益及新增依赖。 |
| 考虑合并 | 没有可用的交付物或局部验收边界，改动总要穿透两边才能完成同一职责；或必须一起生效才能维持同一操作的不变量。不能只因没有独立页面或终端用户流程就合并。 |
| 允许有依赖 | 明确前置输入与输出约定后能单独验收即可；不要求模块完全孤立运行，按需要保留组合验收。 |
| 单列能力模块 | 有实际职责、输入输出和明确消费方即可评估，不要求必须被多个 Feature 使用；仅以公共代码或未来复用为由抽象平台时，仍需证明实际消费需求与完成条件。 |
| 调整粒度 | 依据职责、结果、验收与迭代边界复核；不因模块有名称就自动单列，也不按页面、文件数、预计时长或固定任务数决定。 |

跨 Feature 的长期业务规则可以通过共享 PSC 共同遵守；结合职责、交接和不变量判断是否合并，
不要因为共享一个对象或状态就把所有流程合成一个 Feature。实现同一结果所需的空、失败与恢复路径通常
随该结果一起规划；若异常处理有独立职责、消费方和结果，再判断是否单列。

例如：简单内容发布中的审核可以属于发布 Feature；当审核具有独立队列、转交、退回及单独验收目标时，
可成为另一个 Feature。又如媒体导入、转码处理和分发交付，各自存在产物、消费方和可验证约定时，可以按阶段拆分。
这些仅用于说明判断方法，不是其他项目必须套用的功能清单。

## 检查覆盖、依赖与首批交付

- 每个 REQ/NFR 与 PSC 至少分配给一个 Feature，每个 Feature 同时引用来源需求与总规格合同；检查实际业务
  含义是否被承接，不能仅靠列出 ID 证明覆盖。PRD AC 的结果也应有归属，后续由 Feature AC 展开。
  阶段只承接某条端到端 AC 的部分条件时，写明贡献和组合验证安排，不宣称阶段完成等于该条 AC 已整体通过。
- 每个结果有明确主责 Feature，其他 Feature 可消费其输出；共享 PSC 可由多个 Feature 共同承接。
  不把所有 NFR 或 PSC 无差别分配给所有 Feature。
- 依赖要指出所需的业务状态、数据、能力或输出。区分必要前置与建议实施顺序，不把团队分工或同用一个服务
  当成 Feature 依赖。依赖不得循环；出现循环时检查边界、共享合同或交付顺序，不能靠删掉真实依赖解决。
  开发中的返工反馈不等于循环依赖；可先明确最小输入输出约定，再用样本完善各阶段。
- 根据已确认优先级与必要依赖推荐顺序，说明首批能验证的产物、能力或业务结果。阶段验证可先贯通代表性样本，
  不要求完成全部上游数据或通用平台才开始下游验证；同时保留当前结果必需的业务规则与质量要求。
- 模块内部优化优先验证该模块的产物和直接消费方；输入输出语义或共享状态变化时同步受影响合同和组合验收。
  模块分别通过后，仍须核对 PRD 的完整业务结果，不能遗漏用户入口、后续流程或必要的端到端验证。
- 范围外、已批准延期与 Agent 建议延期要分清；未批准的延期建议不能成为漏掉当前需求的理由。

## 呈报方案与确认

默认给出一套推荐方案，先说明为何采用该拆分主线。每个候选说明名称、可验证结果、范围、来源合同、依赖和
优先级；阶段/模块补充输入输出、消费方、局部验证与迭代边界。用一两句话解释拆分依据，对明显边界不展开长篇
论证；只有真实取舍会改变范围、验收或交付顺序时，才比较备选方案及其影响。

人工重点确认拆分主线、首批结果、能力能否延期、阶段是否需要单独优化及哪些流程必须一起交付。常规归类、覆盖核对和依赖整理
由 Agent 完成，不逐项向用户索要拆分答案。已有材料足以判断时直接推荐；只有无法从来源或当前授权解决、
且会实质改变边界的问题才询问。

仅讨论时直接在对话中呈报，不创建文件。获准落盘后，把最终理由和顺序写入 Map 正文；若已经讨论过，
复用讨论结论，不重复生成一份报告。确认与自行决策的授权边界沿用 SKILL.md；授权只确认 PRD、选择架构
或生成文档，不自动等于允许自行决定 Feature 边界。

完成前检查：每个候选有明确职责与结果；阶段/模块有输入输出、消费方及独立验收与迭代边界；需求和合同无遗漏；
主责明确；依赖可解释且无环；首批结果与最终组合结果的验证分清；重大取舍已按授权处理。
文件格式校验只能验证结构与追踪，不能证明边界合理、模块已解耦或实现已经通过验收。
