# 交互式数据分类与整理

帮助用户通过对话决定“这些资料按什么业务口径整理”。工作顺序是 **识别数据形态 → 独立读取内容 → 推荐业务分类 → 对话修订 → 审核方案 → 按确认结果构建**。主动读资料和提出建议，把分类口径的决定留给用户。

## 范围与默认理解

- 使用用户指定的资料范围和当前有效的业务背景。已有需求、痛点与功能说明足够时直接使用；事实不足时再按项目索引回查相关条目，不默认通读所有背景，也不重新做需求规范化。
- “文件隔离”默认表示每个文件独立读取、保留自身来源与处理结果。第一层按 PDF、CSV、TSV、Excel、JSON、邮件、图片、音视频等形态识别；第二层依据内容和业务需求归类。一个业务类别可以包含多个文件及多种形态。
- 现阶段只确定类别与文件归属，不推断文件间的业务关系，不连接订单与库存等实体，不做跨文件对账、去重合并、本体或知识图谱设计。
- API 是独立的数据来源入口。依据现有接口文档或用户提供的响应记录识别，不把 JSON 文件自动认定为 API。读取现有材料不包含登录、调用远程接口或修改远程状态。
- 资料的内容和位置先保持原样。默认用分类索引引用原始位置；移动、重命名、复制分类副本或生成解析结果，应在具体方案中列明后再执行。不能把“文件隔离”自行解释为搬动文件。

## 推进方式

### 1. 明确本轮范围，识别数据形态

范围已在当前对话给出时直接盘点，不再次询问已知信息。缺少会影响处理范围的关键信息时，只问清这一点。

列出本轮来源及数据形态；扩展名是初步线索，需要时检查实际内容。区分本地文件、接口资料和暂不可读取的来源，给每项分配稳定的清单标识。先汇报简短的类型分布，不从文件名直接得出业务分类。

如果用户只要求盘点类型，到此交付即可，不自动扩展为内容分析或整理执行。

### 2. 逐文件读取，为讨论提供依据

按形态选择当前环境已有的读取能力，例如表格字段与记录、PDF 正文及版面、邮件正文和附件、图像内容、音视频时间片段。不要强制所有格式走同一种解析方式。

对每项记录：读到了什么业务内容、读取到什么范围、哪里仍不清楚。大文件可以先取代表性样本，但要注明样读范围；业务性质还不清楚时继续针对性读取或标为待确认，不以少量样本冒充全量结论。无法读取的内容记录具体限制，不用文件名补猜。

文件内的多种内容可分别记录读取结果；拆分成多个产物、改变文件边界或跨文件合并，需要在后续方案中说清。局部读取问题不妨碍先讨论其他已读材料。

### 3. 围绕一个关键决定展开对话

把已读内容放回用户的业务背景，提出具体可修正的分类建议。不要只问“你希望怎么分”，也不要一次端出已经替用户定案的完整分类体系。

每轮按下面的节奏推进：

1. 简短说明相关材料表达了什么，并给一两个可核对的例子。能从材料中查到的事实先自行查，不转成用户问卷。
2. 给出推荐的业务类别、纳入边界和理由。存在有意义的替代方案时，再提供两三个选项及差别；不为凑选项制造无用方案。
3. 默认只问一个当前最关键的分类决定。依赖这个回答的问题留到后续；用环境支持的提问交互收取回答，没有专用工具时在对话中提问。**收到回答前，不自行代答或推进依赖该决定的工作。**可以继续查阅不依赖该回答的资料。
4. 根据回答简短复述已经确定的口径，调整文件归属和下一问；用户更改前面的口径时，仅回查受影响的部分。已确定的内容不重复追问。

事实、Agent 建议和用户决定分别表述。发现口径与已读材料冲突时，指出具体例子并提出调整建议，不一味附和。用户说“先放着”时记录暂缓，不当作同意。

问题围绕分类粒度、类别边界、多主题文件如何归属、例外和整理方式展开，不延伸成架构评审。足以形成可执行的分类方案后就收敛，不为了走流程持续提问。需要示例时读 [对话示例](references/dialogue-examples.md)。

### 4. 提交具体方案，等待审核

按 [分类方案与结果格式](references/classification-format.md) 维护一份中文 `classification-plan.md`。有实质进展再更新，记录当前口径、已确认决定、待确认事项及必要理由，不记录整段聊天，也不为每轮对话创建新文件。

供用户审核的方案必须已经具体可查：本轮来源清单、业务类别定义、逐项归属、读取限制、要生成什么、输出到哪里，以及是否改变原文件。清单较长时在对话中摘要并链接完整清单，不能只展示少量示例就申请批量执行。

**用户要求的是“审核确定后构建”：在具体方案尚未得到确认时，保持在讨论与方案阶段。**可以读取资料、核对事实、维护草案，不能提前批量创建分类副本或最终解析产物。提出审核后等待用户回答；等待时长、没有反对、只认可某个类别都不等于批准整个方案。

确认按实际语境理解，不要求固定口令。若已展示完整方案，用户明确同意按该方案整理，即可继续执行；当前对话已有同范围授权时直接使用，不再次要求确认。

### 5. 按确认方案构建并核对

执行已确认的类别、文件清单、动作和输出位置。默认生成按业务类别组织的分类索引，各来源保持独立并指回原始位置；用户同时确认了解析结果或目录副本时，再生成这些具体产物。不要顺带搭建通用解析框架、数据库或数据平台。

核对来源清单中的每项都有明确结果或未完成原因，业务归属符合已确认口径，索引位置有效；生成解析内容时保留原文含义和不确定性。复制文件时核对源与副本一致，保留原件。

执行中发现影响已确认分类或整理方式的新情况，只将受影响部分带回讨论，其余已获确认的独立工作可继续。未变的决定不重新审批。

交付分类索引与已生成产物，说明实际覆盖范围及未解决项。暂缓或读取失败的文件不算整理完成，分类相同也不表示已经建立业务关系。

## 存储与已有技能

- 用户指定路径优先。默认将本轮方案与分类结果放在 `docs/04_classify-project-data/`；已有同用途目录时沿用，来源与输出分开，避免再次将输出当作输入。
- 本技能处理业务数据的分类讨论与整理。需求资料规范化继续由 `normalize-project-requirements` 承担；痛点与功能看板继续由 `review-project-requirements` 承担，保留它们原有入口和资源。
- 本技能可独立使用。交互方式参考 Superpowers 的 [brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md) 与 Matt Pocock 的 [grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)（`grill-me` 当前调用的交互逻辑），吸收查明事实、带建议讨论、按回答推进和确认后执行的思路，不依赖安装或运行它们。
