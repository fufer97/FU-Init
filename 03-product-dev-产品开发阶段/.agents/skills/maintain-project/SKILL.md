# 已有项目持续维护

把本轮变更落实到**现有实现、当前有效文档和验证记录**。业务规则、技术栈、目录和检查方法来自当前项目；原型与正式应用沿用同一维护主线，按实际影响选择需要更新的文件。

配置 AGENTS 与 Hooks 是可选的项目接入工作。Skill 指导 Agent 判断和执行变更；配套脚本核对文件与检查证据；Hook 在宿主的指定时点调用脚本。使用 Skill 不等于已安装或启用 Hook。

## 选择本轮入口

- **提出新需求、修复问题或调整已有实现**：执行下方“迭代已有项目”。即使还没有接入 Hooks，也完成已授权的修改与验证，不把配置工作当前置条件。
- **要求建立或调整维护机制**：读取 [项目接入](references/project-integration.md)，维护本项目的 AGENTS、文档入口和 Hooks。已有项目的实际新需求同时存在时，接入后继续完成需求。
- **只讨论方案**：只读检查并说明建议，不改项目或配置。

本 Skill 与项目构建、原型生成等既有 Skills 并列维护。需要某项既有规范时按需读取，沿用其有效合同；不通过修改那些 Skills 来安装本工作流，也不依赖它们全部已安装。

## 迭代已有项目

### 1. 定位同一个项目

读取有效的项目指令、当前实现入口，以及和需求直接相关的设计或规格。分清外层工作区与应用源码目录；按已有入口定位，不凭日期、最新修改时间或默认编号选工程。

先说明本轮要改变的可观察行为、直接受影响的旧路径和最窄验收方法。对已经明确的需求继续执行，仅澄清会改变业务含义或权限且无法由现有依据解决的问题。

按职责识别已有的需求或设计依据、源码、使用说明与验证记录，不按文件名或阶段编号推定项目结构。具体场景的适配示例见 [变更与文件维护](references/change-maintenance.md)。

涉及前端页面、业务命名或导航时，先核对本轮主要对象名称的来源和用户任务，再梳理“入口 → 对象/页面/页签 → 操作结果 → 返回”。有业务名称时不只显示内部代号；缺失名称不猜写，业务编号与原件保留。不要只改一个标题而遗漏直接关联的列表、详情、选择器或结果；详情按任务选择页签/分栏，简单操作不强拆。使用既有设计记录；同级原型 Skill 可用时按需读取其 [应用产品设计方法](../build-frontend-prototype/references/product-design.md)，只复用相关设计方法，不另建原型或扩大为全站改版。

### 2. 判断哪些文件需要跟着变

读取 [变更与文件维护](references/change-maintenance.md)。建立本轮的小范围对应关系：**需求 → 受影响实现 → 要更新的当前文档 → 验证方法**。对看似相关但无需修改的文件，记录具体原因。

- 按产品范围、共享行为、局部功能或实现调整，找到承载受影响约定的现有文件；使用方式变化时同步已有使用说明。
- 原型沿用设计与验看记录；正式项目已有 PRD、Spec 或功能文档时沿用其归属关系。文件名称和数量由当前项目决定，不因调用本 Skill 补建完整文档链。
- 修改文档正文中的当前描述，避免只在末尾追加“已完成”而保留相互矛盾的旧规则。
- 原始来件和客户历史记录保持原文。新需求注明本轮来源和适用范围，不伪造客户批准。

项目已有 `evals/` 或用户要求从 PRD / Spec 生成验收时，使用可用的 `$project-evals` 更新本次受影响的
用例和检查绑定，并把套件、来源、测试数据及脚本纳入验证输入。没有这套格式的项目沿用原有验收，
不将安装新 Skill 或补齐整套文档设为维护前提。

### 3. 记录范围，执行修改

为本轮变更建立轻量运行记录，使用 [检查与 Hooks 协议](references/checks-and-hooks.md) 中的 `begin`。它只保存文件基线、检查结果和会话关联，不复制产品规格；运行目录被忽略，不作为项目事实源。

沿用已有工程、技术栈、入口和状态；修改本轮要求及直接受影响的实现。已有计划适用时继续更新同一份计划与任务，小修改不强制新建 Plan、PRD 或完整文档链。

实现中发现产品含义与原约定冲突时，核对来源及确认关系；不能为了迁就代码而倒改规格。调整本轮文件范围时重新核对基线，不能把已经修改后的文件冒充修改前状态。

### 4. 验证实现，也核对文档的实际含义

用 `run-check` 记录真正执行的检查，方法与本轮可观察行为对应：界面改动检查实际操作，接口改动检查请求、响应与相关调用，脚本改动检查输入、输出及退出结果。只覆盖新行为与直接受影响的旧路径，单独的语法检查或 HTTP 200 不代替行为验证。复用已有、输入未变的有效证据；新增需求不自动证明以前未检查的路径已通过。

前端变更应对照代表性来源核对业务名称，并实际沿变更入口查看目标对象/页签、保存后的结果与返回位置；按设计检查目标视口、必要的列表定位或信息比较。既有链接受影响时核对替代落点。界面名称调整不得改写原始记录或把待批准、已批准、已执行等不同业务状态合并。

已采用 evals 时，以检查 ID 对应运行收据，并在正式记录关联 eval ID；同一个命令覆盖多条用例时仍须
核对各项断言实际执行。来源、用例或数据变化导致的旧证据标为过期；manual 验收记录实际操作，不用
空成功命令替代。结构校验与行为验收分别报告。

在已有验证记录中写入变更 ID、实际方法、看到的结果和未验证项。保留历史未验证状态及其当时适用条件，必要时说明本轮新增了哪一项证据。按需要同步演示路径与恢复方式。

随后对照当前需求，人工或由当前 Agent 审阅：文档是否描述了真实的新行为，直接受影响的入口、调用方和共享状态是否一致，未涉及的业务规则是否保留。`check` 只能检查文件、范围和证据有效性，不能证明业务含义一致。

使用 `finish --review <具体核对结果>` 收尾。检查失败时修正实际问题；未运行或无法验证时如实交付待验看状态，不标成完成。

### 5. 交付

说明用户现在能做什么、改了哪些实现与文档、验证了哪些路径，以及剩余限制。给出已有项目的入口；不另建 `v2`、`new` 或日期工程。

当前授权范围完成即停止。接下来在同一会话提出的新需求重新确定范围，下一次会话从更新后的现有文件接手。

## 检查资源

- [变更与文件维护](references/change-maintenance.md)：变更分类、当前事实、历史、跨会话接手。
- [检查与 Hooks 协议](references/checks-and-hooks.md)：三者分工、运行记录格式、命令、证据失效与事件处理；实际脚本为 `scripts/maintenance.py`。
- [项目接入](references/project-integration.md)：仅在配置或修改 AGENTS / Hooks 时读取。

`scripts/maintenance.py` 使用 Python 标准库。其检查结果与 Skill 的语义判断分开报告；不调用付费模型、不安装参考框架、不依赖真实后端。
