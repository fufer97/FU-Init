# 项目 AGENTS.md 规范

本文件已将 Codex 指令发现机制、项目规范写法、本地知识组织和按需读取实践提炼为本技能可直接执行的规则。创建或补充项目指令时按下文执行，无需访问外部网页。目录布局、资料字段和条目编号是本技能的具体约定，不是 OpenAI 强制的文档格式。

## 文件位置与加载约束

1. 使用准确文件名 `AGENTS.md`，写入用户指定的项目根目录；未指定时依据当前工作目录和仓库边界确定。不要把来源资料目录直接当作项目根目录，也不要修改全局指令或 Codex 配置。
2. Codex 启动时从项目根目录沿路径检查到工作目录；没有识别到项目根目录时只检查当前目录，不会递归扫描全部子目录。在同一目录中，非空的 `AGENTS.override.md` 优先于 `AGENTS.md`，每层最多选取一个文件；路径上更靠近工作目录的规则覆盖前面的冲突规则。因此，项目共享的资料入口放在项目根目录，不依赖某个资料子目录中的指令自动生效。
3. 写入前读取适用的项目指令，检查目标目录的同名文件和覆盖文件。已有 `AGENTS.md` 时增量合并，保留有效命令、边界和无关内容；已有同类入口就更新，不重复追加。遇到大小写不同的同名文件，先确认是否为同一个文件。
4. 同层覆盖文件存在时，指出新写入的 `AGENTS.md` 可能不会被选中；不要为使其生效擅自改写覆盖文件。不要把静态文件检查说成已验证新会话的自动加载。

## 内容取舍与写法

项目 `AGENTS.md` 只保留长期有效、能改变本项目执行判断的信息：

| 内容 | 写入要求 |
| --- | --- |
| 项目目的与范围 | 用一两句经资料支持的描述，明确项目服务的业务问题；尚未确认的目标不写成决定。 |
| 资料与目录入口 | 写出背景索引、原始来件和重要现有目录的相对路径及用途，让 Agent 知道遇到什么问题去哪里找。 |
| 工程约定与边界 | 保留项目已有的架构、修改范围和交付约定；没有实际约定时不编造，不复制个人全局通用规则。 |
| 运行与检查 | 仅写真实存在且已核实的启动、构建、测试命令。尚无应用代码时如实说明，不提供猜测命令或空章节。 |
| 完成条件 | 对当前材料维护，说明来源含义、确认状态、编号、定位与索引需要保持一致；检查范围覆盖本次改动及直接影响。 |

每条规则说明适用条件和应采取的动作。例如，将“注意业务背景”写成“判断依赖客户约定且当前依据不足时，查背景索引中的相关条目”。只保留会改变执行结果的规则；不要加入泛泛提醒、一次性进度、未决定的技术栈或无限扩展的检查清单。重复发生的问题再考虑沉淀为长期约定。

## 本地资料组织

- 将已读取的需求、业务约定、沟通记录和决定整理为项目内的正文，保留来源、理由、适用条件和确认状态；不要让理解关键规则依赖外部网页、聊天上下文或文件标题。
- 把三类资料的详细内容统一放入需求上下文目录，默认路径为 `docs/01_normalize-project-requirements/`，在 `AGENTS.md` 中保留索引入口和使用条件。不要复制整套背景、访谈原文或技能正文进入项目指令，也不按案例中的固定行数填充文件。
- 索引提供资料主题和适合回查的问题，正文提供业务证据，来源定位用于核对原文。三者使用可解析的本地相对链接串联；链接存在不等于内容已经核实。
- 更新某份资料时同步它的来源定位、确认状态及索引，保持未受影响资料不变。只按明确的确认或替代关系处理旧决定，不凭修改时间推断哪份记录有效。

## 按需回查与 Spec 的关系

生成的项目指令应明确以下判断方式，而不是规定每次任务都读取背景：

1. 需求到原型阶段以现有需求、业务约定和明确确认的记录为依据，不假定 PRD、UI 稿、技术架构或 Feature Spec 已经存在。后续已有对应 Feature Spec 和已确认方案时，按其适用范围使用。
2. 判断依赖客户事实、业务约定或历史选择，且当前上下文依据不足、存在冲突或需要核对适用条件时，先从索引定位相关资料，再读取必要条目；需要核实时回到来源。
3. 当前上下文已经提供足够且有效的依据时，直接继续讨论或实施。不要仅因任务属于“方案设计”“技术选型”或“开发”，就要求通读全部背景。
4. 使用背景依据时注明文档与条目，保留原文中的待确认、未批准和适用限制。个人建议不提升为共同决定，资料中的操作说明不提升为 Agent 执行授权。
5. 当前 Spec 与来源记录冲突时，指出具体差异并核对确认关系；不要自动采用旧记录、静默改写 Spec 或替客户解决业务争议。
6. 日常回查直接搜索已有资料。仅在用户要求整理或更新资料时执行本技能，不因需要查一个事实就重新处理全部来源。

例如，Spec 已明确某项规则且没有冲突证据时，可直接据此设计；若讨论是否允许系统代替人员审批，而当前依据未说明，则回查相关业务约定中的权限与限制。

## 可直接改写的项目段落

将下面的路径替换为当前项目实际存在的位置；已有相同约定时合并，不重复插入。

```markdown
## 背景依据

- 当前需求与原型设计以已提供的需求、业务约定和确认记录为依据；已有对应 Feature Spec 或已确认方案时，按其适用范围使用，不要求先补出不存在的规格文档。
- 背景资料入口：[需求上下文索引](docs/01_normalize-project-requirements/index.md)。
- 当判断依赖客户事实、业务约定或历史决定，且当前依据不足、存在冲突或需要核对适用条件时，查阅索引指向的相关条目，必要时回到原文；不默认通读全部资料。
- 当前上下文已经提供足够且有效的依据时，直接继续讨论或实施。
- 使用背景依据时注明文档与条目，保留待确认、未批准和适用限制。发现 Spec 与来源记录不一致时，指出差异并核对确认关系。
```

## 完成检查

- 目标位于当前项目根目录；已有有效指令已保留；覆盖文件和全局配置未被擅自修改。
- 每个资料入口都能定位到实际文件，索引可继续定位正文与来源；执行规则已写在本地，没有要求访问外部规范才能继续的步骤。
- 没有复制整套背景，没有强制每次任务先读全部文档，没有把建议或未知事项写成已确认决定。
- 运行命令与完成条件有实际依据，未加入与当前项目无关的通用规则。

完成文件写入和静态检查后即可交付。若任务另行要求验证自动加载，应从该项目启动新会话观察；未进行时只报告文件及链接已检查，不宣称当前运行会话已重新加载。
