# 客户痛点与功能看板

使用本技能处理“根据这些文档生成看板”“梳理客户痛点和要做的功能”“说明功能能达到什么效果”等请求。默认填充用户已确认的浅色三列模板，让人直接读懂 **客户痛点 → 对应功能 → 预期效果**。全部关联直接展示，不需要先切换视图或打开详情。

这是需求到原型流程的 **02 需求看板阶段**：读取 01 阶段需求资料或用户指定文档，向后续原型设计提供痛点、拟做功能和预期效果。本技能不创建 03 设计记录或 04 前端工程，也不把看板内容自动视为甲方已确认。

看板用于说明要解决的问题，不直接决定未来系统的菜单、页面和操作步骤。后续原型应结合用户希望呈现的方式，编排未来使用场景；不要把每一行机械转换成一个后台模块，也不要把本看板的版式当作业务系统的 UI 模板。

## 先提炼业务内容

1. **读取相关文档**：以用户指定的资料为准。有规范化索引时先定位相关条目，本项目默认入口为 `docs/01_normalize-project-requirements/index.md`。没有索引时直接读取指定文档，不强制先重跑资料整理。客户需求说明诉求，沟通记录补充实际困难，业务约定限定功能的适用条件。
2. **先列痛点**：写客户当前遇到的具体困难及影响，例如“事情交出去了，结果跟不住”。痛点应有文档依据，不把功能名、技术选型或个人设想写成客户痛点。
3. **关联功能与效果**：为每项痛点说明接下来做什么功能、包含哪些主要动作，以及预期改善什么业务结果。功能回答“系统做什么”，效果回答“客户因此能看清、判断或完成什么”。一行表达一组清楚的对应关系；按实际内容决定条目数，不凑固定五条，也不强制痛点与功能严格一对一。
4. **核对表述**：原文未规定的准确率、响应时间、节省比例、日期和责任人不能编造。新增建议、待确认条件和预期效果不能写成已批准决定或已实现成果。对功能有实际影响的业务边界，简要写入对应行或页脚。

## 默认页面与生成方式

- 先读取 [三列看板模板](assets/board.html) 和 [看板数据格式](references/board-data.md)，基于模板填充内容。页面采用用户于 2026-09-29 确认的复刻版式：暖白底色、红／绿／蓝三列、圆角卡片、编号与图标、顶部玻璃卡片和绿植装饰。左列列举客户痛点，中列说明拟做功能，右列说明预期效果。
- 默认保持标题区、范围标签、阅读设置、三列列头和逐行关联结构。业务内容写入数据，复用 [行模板](assets/board-row.html) 与 [装饰素材](assets/illustrations/)；不要把模板仅当作灵感重新设计，也不要嵌入整张参考截图。桌面显示三列，窄屏按每组“痛点、功能、效果”纵向阅读。
- **允许随内容调整**：客户名称、范围标签、需求行数、每行动作数，以及容纳内容所需的卡片高度和换行。行数不固定为参考图中的四行，不裁掉长文或省略业务边界来凑版式。只有用户提出新视觉要求时才调整相应样式。
- 默认包含字号、行距与留白调节及恢复默认按钮，由 [阅读控件](assets/reading-controls.html) 提供。`reading_controls` 缺省或为 `true` 时启用；用户明确需要无控件的静态版本时设为 `false`。
- 默认不加入文件清单、来源关系图、评论、审阅状态、筛选、视图切换、导出或“复制提示词”。不要因为另一个模板包含这些功能而自动带入；只有用户明确需要时才增补。
- 来源文件、条目或页码保留在项目数据中，用于生成时核对；页面不显示技术编号或文件追溯入口。看板描述客户未来要用的“资料查询”功能，与看板自身增加文件浏览器是两件事。
- 按数据格式写入 `board-data.json`。客户名称、具体痛点、业务规则及来源路径放在项目数据中，不能固化到技能、生成脚本或模板。
- 新建时固定使用 `docs/02_requirement-playground/board-data.json` 和 `index.html`，都相对于容纳需求资料的工作区根目录。已有用户认可的页面或项目明确入口时，在原位置更新；不因采用新版编号约定另外生成一份同用途页面。用户要求迁移时，同步来源路径、页面入口和项目指令，不留下两份当前版本。

新建看板的生成命令（已有页面时替换为其实际路径）：

```bash
python3 .agents/skills/review-project-requirements/scripts/build_board.py \
  --input docs/02_requirement-playground/board-data.json \
  --output docs/02_requirement-playground/index.html
```

脚本只读取数据中明确列出的来源，检查文件校验值，并将提炼结果填入模板。它不自动理解文档；内容取舍、关联是否成立及来源定位必须先由 Agent 核对。源文档变更时先复核相关内容，再更新数据中的校验值。HTML 为可再生输出，项目数据和模板是生成依据；不要只改输出 HTML 而使下次生成丢失修改。图标与绿植来自已确认参考图的独立裁片，生成器将其内嵌，输出不依赖原图或外部资源。

## 验证与交付

- 检查每行三者是否对应：功能确实针对所述痛点，效果说明业务改善，不只是重复功能名称；来源支持关键判断，未知事项仍明确。
- 用脚本实际生成页面，核对行数、业务文字和边界完整，内嵌素材、CSS、JS 可离线使用。检查阅读调节及恢复默认行为。
- 按当前会话允许的方式对照模板检查标题区、三列层级、配色、留白和窄屏阅读。允许浏览器验证时优先使用内置 Browser（`iab`）；用户要求自行验看或禁止自动化时，交付实际预览入口并如实说明未做自动视觉验证，不绕过限制。需要在线预览时启动本地静态服务。
- 给出页面入口及必要的待确认说明，不把生成看板说成业务功能已实现。保留原始文档和无关技能，不改写业务确认状态。

## 用户明确需要详细审阅时

只有用户另行要求文件追溯、需求与约定关系、评论或意见导出等详细审阅能力时，才读取 [详细审阅数据与交互](references/review-data.md)，使用已有的 `scripts/build_panel.py` 与 `assets/panel.html`。这些资源继续保留，不作为普通“生成看板”请求的默认流程。

`playground` 的六个通用模板独立保留。由 `$playground` 转入本流程时仍以本技能的三列模板和生成器为准，不叠加通用 playground 的提示词输出、预设或审阅工作流。
