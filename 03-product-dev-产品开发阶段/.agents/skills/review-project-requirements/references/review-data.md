# 详细审阅数据与交互

仅在用户明确要求文件追溯、关系浏览、评论或意见导出时使用本流程。普通“基于文档生成看板”请求按 `SKILL.md` 的三列看板流程执行，不加载本流程的交互要求。

本文件定义 HTML 生成器的输入，字段名是技术接口，字段值和界面使用中文。每个项目仅维护一份 `review-data.json`，不要创建同内容的中英文副本。

## 数据结构

- `schema_version`：当前为 `1`。
- `project`：`id` 为稳定的项目标识；`title`、`subtitle`、`summary`、`scope` 为有来源的中文说明；`as_of` 为资料截止日期；`review_note` 说明需要人工确认的边界。
- `sources`：明确列出的规范化文档，每项包含 `id`、相对于本 JSON 的 `path`、该 Markdown 当前内容的 `sha256`。不得把整个原始交付目录作为输入。
- `items`：审阅事项列表，格式见下表。
- `relationships`：需求与其他事项的显式关联，格式及判断要求见“需求关联”。

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定且唯一的面板事项编号；不是新业务单号 |
| `category` | `requirements` 客户需求、`agreements` 业务约定、`communications` 沟通进展、`materials` 资料现状、`questions` 待确认事项 |
| `title` / `summary` | 名称与简短摘要 |
| `origin` | `原文明确`、`依据记录归纳` 或 `整理建议，待确认` |
| `fields` | 若干 `{label, value}`，按事项性质取舍说明，不强制填空模板 |
| `references` | 来源条目编号数组，例如 `REQ-001-02`，必须真实存在 |
| `date` | 可选；沟通发生日或明确标注的补充日，不能用文件修改时间代替 |

规范化 Markdown 使用 YAML frontmatter 的 `id`、`type`、`source_date` 和首个一级标题；条目标题为 `## 稳定编号 标题`。生成器兼容这些简单标量，不负责通用 YAML 转换。

## 内容编排

- **客户需求**：展示客户诉求、拟提供能力、完成标准、适用范围与关联约定。明确的原话可直接引用；从多个段落提炼的功能表述标为归纳，新增建议标为待确认。没有量化指标就展示待量化，不能填写虚构准确率、响应时长或开发完成率。
- **业务约定**：保留适用对象、条件、审批责任、例外和有效范围。案例报价与预计时间不自动变成普遍规则。
- **沟通进展**：按原始访谈时间和补充时间分别列项，说明沟通内容、明确的共识或岗位意见，以及还需核对的事项。“有记录”不等于“已全部对齐”。没有下次沟通时间就不编排日期。
- **资料现状**：只描述需求与访谈中提及的系统、资料类型、分布、更新节奏和缺口，注明是记录所述。不得以本面板生成过程为由进行数据盘点或连接系统验证。
- **待确认事项**：说明待确认问题、确认后的用途、原文是否指定负责人。建议向谁核对必须标“建议”，不自动分派任务。

同一约定可被多个功能引用，不需要复制为多份约定。资料与沟通多少由来源决定，不预设数量。

## 需求关联

每条关联包含：

| 字段 | 含义 |
| --- | --- |
| `requirement` | 起点，必须是 `requirements` 分类的事项编号 |
| `target` | 终点，必须是已存在的约定、沟通、资料现状或待确认事项编号 |
| `reason` | 这项内容为什么与该需求有关，尤其说明约定限制了什么行为或条件 |
| `references` | 支持这项关联的来源条目，必须覆盖起点和终点各自的依据 |

按业务含义判断关系。两项内容引用同一文件、同一通用段落或相似词汇，不足以证明关系。不要把所有约定无差别连到所有需求，也不要从某段访谈存在推断整场沟通已经完成对齐。

需求的对应文件从其直接来源与显式关联的证据条目归集，显示真实文件名，并能查看与这条需求有关的条目。共用文件或约定可以反向关联多个需求；缺少关联要标为待建立，不自动解释成没有约束。

关联视图以当前需求为持续上下文。打开关联的约定、沟通或来源后，仍能返回原需求；主动选择另一条关联需求时才切换。原有分类列表继续提供另一种浏览方式，并能返回需求关联页。

## 审阅结果

页面为每个事项记录 `status`、`comment`、`updated_at`，并关联项目和资料版本。此信息属于人工审阅意见，不能修改原始 `origin` 或把来源中的“未批准”改为“已批准”。

导出的 Markdown 供人阅读或交给 Agent 修订；JSON 保留项目、版本、事项编号、对应文件、相关需求、关联约定及理由、审阅状态、评论和记录时间。仅纳入实际产生的审阅意见及其关联上下文。复制修订意见应说明修改目标、依据和人工意见，不直接执行业务动作。

`revision` 根据来源与审阅事项内容计算，`relationship_revision` 根据关联整理计算。只修改关联或布局时不清空原有事项的评论；旧的事项确认不表示新增关系也已经被确认。

浏览器本机保存是单人使用方式。页面可通过 HTTP 分享，但不同人的审阅结果不会自动合并；需要共享保存时应单独设计，不宣称静态 HTML 已支持多人协同。

## 生成与检查

新建详细审阅面板时放在 02 阶段目录，使用独立的 `review.html`，不覆盖默认看板 `index.html`。已有项目按其实际详细审阅入口执行，不因下方示例搬迁旧页面。

```bash
python3 .agents/skills/review-project-requirements/scripts/build_panel.py \
  --input docs/02_requirement-playground/review-data.json \
  --output docs/02_requirement-playground/review.html
```

来源变化后先复核内容和关联，再更新数据。实际打开页面，检查需求与文件、约定的关系、上下文内查看及反向定位，以及搜索、分类、审阅保存和导出路径。验证后清除测试评论。已有详细审阅入口、数据和意见不因默认看板流程改变而删除。
