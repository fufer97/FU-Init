# 工作流与证据衔接

## 消费现有成果

| 现有成果 | 交付时的用途 | 不应推定的结论 |
|---|---|---|
| PRD、总 Spec、Feature Spec 或同职责文档 | 范围、业务条件、AC / PSC、明确排除项 | 规格中出现就等于已经实现 |
| Plan、Tasks、变更记录 | 定位实现、遗留工作、历史决定和相关检查 | 勾选完成就等于实际验收通过 |
| 代码、构建配置、锁文件、接口和迁移 | 确认入口、依赖、运行方式及实现版本 | 有源码就能在任意环境部署 |
| evals、原生测试及验证记录 | 复用用例 ID、预期、实际结果与证据 | 用例覆盖或结构校验就等于行为通过 |
| 维护记录 | 定位本轮已变更文件和真实运行结果 | 一次维护收尾就等于整个系统已验收 |
| 用户反馈、培训和试点记录 | 采用情况、未决事项、岗位接手和真实效果 | 已发送材料就等于培训、签收或产生收益 |

标准工程使用 `docs/verification/` 作为正式验证结论入口；维护脚本的收据、原生测试日志和截图可以被它引用。运行目录可能被清理：交付仍需要的唯一证据应保存到项目约定的证据存储，再更新引用；不把临时绝对路径作为接收者唯一入口。

已有 `$maintain-project` 负责代码与有效文档同步，已有 `$project-evals` 负责用例、执行和验收记录。本 Skill 汇总它们的结果，不重建维护状态机、不替换用例库、不自动安装 Hooks。其他工程按相同职责复用原流程，不依赖这两个 Skill 必须安装。

## 保留验收状态及适用范围

| 原结果 | 交付报告的处理 |
|---|---|
| `pass` | 引用真实证据与适用版本；只对所覆盖条目报告通过 |
| `fail` | 保留不满足的预期、实际结果、影响和整改去向 |
| `not_run` | 说明尚未执行及下一步，不改成“待补截图但已通过” |
| `blocked` | 写明缺少的环境、资料或授权及解除条件 |
| `error` | 记录运行或基础设施异常，不能当作业务通过或正常失败 |
| `stale` | 说明哪些输入已变化；只重验受影响项 |

复用证据时对照记录中的代码版本、未提交改动指纹、规格、测试数据、检查实现及必要配置。无版本记录且无法建立对应关系时，标明有效性未确认，不能因文件较新就视为当前结果。生成交付清单的新哈希只能证明现在的文件内容，不能补证过去运行时用的版本。

交付范围先从用户要求和有效合同确定，再核对所有范围条目；不能从“目前通过的用例”反向挑选范围。局部交付可按用户限定范围完成，总体验收仍有缺口时保持独立披露。

发现失败、证据过期或文档/实现冲突时：

1. 只修正文档描述即可消除的事实错误，直接修正并更新引用。
2. 需要补验且已有授权时，按项目原生方式执行一次必要检查，更新原验证记录。
3. 需要改代码或改业务约定时，沿用已有开发/维护授权；没有授权就记录问题和处理入口，继续交付其余材料。

不得用新报告覆盖历史失败，或把交付说明中的建议写成已批准的产品规则。

## 材料、接手、签收分别确认

- **材料状态**：所需文件存在、内容可用、链接和版本可核对；缺项有明确说明。
- **业务验收**：合同要求的功能和跨功能行为是否有适用的通过证据。
- **接手验证**：目标角色是否在相应环境完成了运行、操作或恢复任务；只检查手册文字时明确为文档核对。
- **用户签收**：谁、何时、对哪个版本和范围作出什么确认。没有记录就写未签收，不预填姓名、日期或默认接受尾项。

企业试点和业务影响依赖真实观察。报告指标应列基线、统计周期、样本范围、口径、实际结果及限制；只有预估或演示数据时注明尚无真实效果证据。培训材料可先制作，参加记录、操作结果和正式交接只能记录已经发生的事实。
