# 项目交付与接手

让接手者不读聊天记录，也能找到本轮交付范围、运行和使用方式、验收依据及剩余责任。复用项目已有文档，只补缺失内容；文档描述当前真实实现，不另建一套产品规格。

## 定位范围与事实源

先读取适用 AGENTS、项目入口和用户指定范围，确定实际应用根、接收对象及交付版本。外层资料区不是应用工程；已有原型或局部成果按原范围交付，不自动升级为生产系统。

- 已采用标准工程时，读取本轮相关的 PRD → Product Spec（PSC）→ Feature Spec / Plan / Tasks、当前代码、`evals/` 和 `docs/verification/`。
- 其他工程沿用已有需求、测试和文档入口，不为调用本 Skill 补建整条文档链。
- 业务约定说明应该做什么，当前代码说明实现了什么，运行记录说明实际验证了什么；文件名、Task 勾选或一次构建成功不能替代验收。
- 用户只要求设计交付方案时只读讨论；要求整理或更新交付材料时，直接完成本地文档和清单。外部发送、发布、部署及签收按已有授权执行，生成文档本身不增加这些权限。

先简述本轮范围和核查方式。普通目录与文件名可自行沿用现有约定；仅当缺失信息会改变交付范围、接收权限或业务结论时询问，并继续其余工作。

## 1. 核对当前成果与验收依据

读取 [工作流与证据衔接](references/workflow-and-evidence.md)，建立“范围条目 → 当前规格 → 实现入口 → 验收结果/证据 → 交付材料”的对应。沿用原有 ID；跨功能的产品验收与单个 Feature 结果分别说明。

检查证据适用的代码、规格、样本和环境。复用输入未变的有效结果；缺失、过期、失败和未执行保持原状态。需要补验时使用项目原生检查，项目已有 `$project-evals` 时沿用其用例与结果格式。不要为记录同一结果重复执行检查。

发现问题按已有授权处理：交付文档错误在本轮修正；代码缺陷或产品规则冲突回到项目维护流程，已有修复授权时继续完成相关修复和验证，否则记录缺口。不能为了交付而降低验收条件或把计划中的功能写成已实现。

## 2. 整理可接手的材料

读取 [交付材料规范](references/delivery-documents.md)。默认在实际应用的 `docs/delivery/` 维护交付入口；已有同职责目录就继续使用。它是当前交付文档的维护位置，输入来自现有工程，版本变化时更新受影响内容，不按日期复制整个项目。

按项目实际情况提供五类内容：交付总览与清单、验收报告、部署运行手册、使用培训材料、交接记录。已有 README、运行手册、测试报告或用户文档能回答问题时直接引用并更新，不另外复制同一正文。无数据库、无模型或不涉及生产运行的项目说明相应项不适用，不补虚构配置。

默认使用简体中文 Markdown。用户另有格式要求时采用相应文档工具，并检查最终格式；不默认生成 Word、PDF、媒体或 ZIP。范围内的已知问题、未提供环境、未实施培训和未发生签收要具体记录，不能用空模板占位后宣称完成。

## 3. 核对接手方式与文件版本

使用说明中的命令来自项目真实入口。复用已验证且仍适用的安装、启动、操作及恢复记录；有需要且在授权内时，只补做尚缺的最窄验证。没有运行环境时记录未验证项和复现步骤，不把文档已写好当作换机或生产验证成功。

读取 [交付清单与检查](references/manifest.md)，列出实际要交付的文件和用于核对版本的输入，生成同目录 `delivery-manifest.json`。执行 `delivery_manifest.py snapshot` 保存当前字节指纹，再用 `check` 核对清单。脚本只读显式列出的文件，不收集整棵目录、不执行项目命令，也不判定业务通过。

源码以现有工程或明确版本的源码包为入口；清单列出的文档不自动代表全部源码已打包。只有用户要求独立复制或压缩交付时，按接收范围组织可运行源码、必要资产和依赖说明，排除凭证、无关原件、缓存及依赖树，并核对目标中的相对链接和运行入口。内部材料不能随客户包自动分发。

## 4. 交回结果

说明交付入口、版本与范围、实际核查情况、已知限制及下一位接手者需要做什么。分别报告材料完整性、业务验收、接手验证和用户签收，不能合并成一个“全部完成”。

已有证据不足时仍交付可用材料，并列明缺项、影响、责任岗位和下一步；不伪造负责人或承诺日期。后续反馈继续更新同一项目，维护流程修正实现和规格，验收流程更新受影响结果，本 Skill 同步相应交付说明与清单。

交付范围内材料已整理、引用及版本检查通过，且所有未完成事项均如实披露后结束。不要为生成更多文档扩大功能范围，也不要把这次材料交付称为客户已经验收。
